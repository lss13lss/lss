# Lauren Tan 详解 GrokBot 实战：如何把 agent 用到「醒来已有 20 个 PR 合并」

> 来源：B 站 BV1MWtv6QENj｜UP 主：小龙虾学长｜原标题《【Grok中配】2026-Lauren Tan详解xAI GrokBot实战》
> 讲者：Lauren Tan（X/Twitter 上叫 Potato，**拼写里带一个 e**，即 @poteto）；加入 Cursor 五个月，此前在 Meta 做 React Compiler，再之前在 Netflix 做了约两年的 tech lead 转工程经理
> 时长：59 分 41 秒（3581 秒）｜发布日期：2026-09-04｜本页面转自 **P1 中文 AI 配音版**
> 转写：whisper large-v3-turbo + Vulkan（AMD RX 6750 GRE），228.8 秒，1520 段，1.8 万字
> **额外做了术语校准**：同一视频的 P2 是英文原声，我另外跑了一份英文转写（`-l en`，231.5 秒）用来核对人名与产品名，下文的术语修正大多有英文原稿佐证。

**一句话概括**：用 agent 的瓶颈从来不是「生成代码」，而是「你怎么信任它产出的东西」。信任要靠三样东西堆出来——**验证能力**（agent 能自己跑起来看结果）、**技能**（把工程师的判断力编码成 markdown）、**架构与 CI 硬约束**（让走捷径的那条路恰好就是正确路径）——堆到一定程度，你才能在 main 分支上事后 review agent 自动合并的 PR。

**立场声明**：以下全部是视频讲者的观点与实践方式，**不代表本人立场**。其中的吞吐数字（月 1000 PR、600+ 重构 PR）建立在「AI 实验室里 token 无限」的前提上，讲者自己也提示了 ROI 权衡，请勿直接照搬。

## 一、开场：管理与管 agent 是同一件事

- 讲者背景串起来正好是一条有意思的路线：**Netflix（tech lead → 工程经理，约两年）→ Meta（React 团队，React Compiler）→ Cursor（五个月，受邀支援 agent window）→ 现在做 GrokBot**。
- **全片的方法论骨架就是这个类比**：「在管理技能和管理 agent 之间有很多相似之处」，所以讲用一个段的篇幅把它讲透。
- 她在 Cursor 的经历有点歪打正着：本来要加入云 agent 团队，因为 React 背景被拉去救 Agent Window（这是个 React 应用），而 Agent Window 一周后就要发布。
- 一句轻松的开场白：「**已经是 2026 年了，我还是不知道怎么用 Zoom**」。

## 二、核心命题：信任曲线，而不是并行度

- **工程师的信任是怎么丢的**：写了很多年代码的人有自己的工程标准和踩坑经验，而 agent 会猜、会幻觉、**第一百次自信满满地宣称「找到了确凿证据（smoking gun）」，结果根本不是真正的问题**——这样几次下来信任就没了，你也就没法真正把 agent 用满。
- 管理类比：不信任团队 → 只能微观管理 → 你会一直盯着每个人的输出。agent 同理。
- **一句话结论**：「如果你连一个 agent 的输出都不信任，你就不可能一下开出一百个。」
- 她画了一张「信任 × agent 数量」的曲线（纵轴信任、横轴并行数量）：
  - 起点是**和一到两个 agent 紧密合作**，每一条输出都看、每个 tool call 都读，**根本无法并行**；
  - 五个月里她把这条信任曲线推了上去；
  - 终点是：**「我今天醒来的时候，大概有 20 个 PR 已经被（agent）合入了，我在 main 上 review 了一下，它们都不错。」**
- 吞吐数字（她自己强调不是炫耀，而是展示曲线的形状）：第一个月效率很低（在熟悉代码库），**上个月提交了 1000 个 PR，这个月才到 12 号已经快 800 个**。
- 她的坦诚回应：「我相信你们很多人会质疑——这些代码到底有多好？我觉得这样质疑确实很合理。」

## 三、第一个基础设施：验证（Verification）

- **定义不是「跑测试」，而是 agent 能真的把程序跑起来、像用户那样操作它**：实际运行代码、**抓 CPU trace 和堆快照（heap snapshot）**、打开 iOS 模拟器，去验证用户实际会看到的行为。
- 「这**不保证**你的 agent 能写出好代码，但至少能让它们写出**正确的**代码——对能否信任你的 agent 来说，这是非常大的一步。」
- 反过来的情形（她入职第一周的真实经历）：自己一个人做 Chrome DevTools 性能追踪、截图、下载 trace 发给 agent，agent 自信地说「就是这个东西」，结果根本不是；**「没有验证技能时，你就是验证者——也就是说你是瓶颈。」** 于是你在「agent 写 → 你开本地构建 → 截图/控制台报错粘回去」的循环里出不来。
- 于是她做了 **Control Glass 技能**（Glass 是 agent window 的内部代号）：通过 **Chrome DevTools Protocol**（iOS 侧用 Apple 提供的模拟器工具）让 agent 自己驱动应用、取 trace。**这类技能本身不难写，agent 就能帮你写——真正缺的是下面那个文件。**
- **关键增量：Feature Map（功能地图）**。agent 会跑应用了，但**完全不知道这个应用有哪些功能、怎么走到那里**——用户报告「左侧边栏有点卡」「右边的 PR 页卡了」，它得先花大量时间找代码。Feature Map 把「侧边栏是什么、有哪些子功能、从用户视角怎么走过去、有哪些快捷键、甚至用于 CDP 选择元素的 DOM 属性」全部写进去。有了它，**一个模糊的报告甚至一张截图就能映射到代码库**。
- 落地方式：`pstack` 里提供了 **create verification skill** 和 **maintain verification skill**，让它自动探索代码、生成并维护这份 feature map。

## 四、技能为什么会有效：「把 agent 拉进另一个潜在空间」

- 触发点是她发现：agent 一口咬定「一定是这个」，但**查看实际 tool call 时发现它根本没读应该受影响的那段代码**。「那一刻我就觉得我再也信不了这个 agent 了。这样很容易积累不信任、感到无助。」
- 管理类比救回来了：想象你团队里有个**很会写代码但完全没有业务背景、五秒前才入职**的工程师——你怎么让他变高效？答案是**教**，而教的载体就是技能。
- 「**技能其实就是 markdown**」，但它编码了大量信息、指令和工作流。她的机制解释（这段很值得单独记）：
  > LLM 本质上是在预测下一个 token；**当你一开始给它一些高质量的 token，它就能在更高维的空间里做模式匹配**，那个空间更「聪明」。推特上有人把这叫「把 agent 拉到另一个潜在空间（latent space）」，说白了就是这么回事。
- 对应还有一个观感提醒：只看 tool call 就行，别被表面的自信糊弄过去。

## 五、Evals：把技能当单元测试跑

- **`pstack` 的来历**：Y Combinator 的 CEO **Garry Tan** 做了个叫 **gstack** 的插件，两人同姓但没关系，她就开了个玩笑，把自己的叫 **P-Stack（土豆堆栈/Potato Stack）**，再按自己的工程习惯改了改。它**不是规划出来的**，是从一堆零散技能长出来的。
- **建设方式极其朴素**：早期她对每个细节都极度挑剔，**每次观察到一种失败模式，就把它固化成一个技能**——「别再瞎猜了，去搜索、去查代码、多用一些子智能体」。
- **Eval = 技能的单元测试**，落在 `pstack` 里就是 **Eval Playbook**（在 Potato Mode 下）。做法是：
  1. 让主协调器 agent 先写一份 rubric（评分标准），说明我希望这个技能做到什么；
  2. 生成大量子 agent，**给它们各自独立的目录，并「巧妙地命名」使子 agent 不知道自己正在被评估**——「因为 agent 真的能看出来，一旦看出来它们会改变行为」；
  3. 跑分并对结论交叉验证：**用一个不同模型的评判 agent 来打分**，避免单一模型有偏见；
  4. **爬山式优化**：继续在这个评估上循环，直到全项拿满分。每次改技能都跑一遍。
- Cursor 支持很多模型 → 可以在不同模型矩阵上看技能表现。
- **但维护技能很难**：需要品位和观察。她给的心法是**当好一个「后座司机」**——像结对编程那样盯着同事写代码、心里想着「你会做得更好，为什么没这么做呢」；实操建议是**打开所有 tool call、读代码读取、读 agent 的 thinking blocks**，从中找失败点。

## 六、先本地再云；别急着开一百个

- **起点建议在本地**：因为你能亲眼看到 agent 与应用的交互过程、能看到它调用哪些 API。
- 她本人则基本全押**云 agent**：「只要在配置环境上花一点时间，这些 control 技能和验证技能会带来巨大的回报——因为它不只是让你一个工程师变好，是让你**整个团队、甚至整个公司**都升级。」
- 例子是他们的 **Benny**：接到用户 bug 报告后，自动在云端拉起一台自己的电脑、在上面跑 Cursor，**用同一套 Control Glass 技能去复现**；有一次它复现出的 bug 在 main 上其实已经修好了——这一条信息就省掉了她一小时的对线。
- 明确的逆序警告：**别从「低信任」直接跳到「一百个甚至几千个云代理」**，那只会烧钱烧 token。

## 七、第三部分：重新考虑「重写」

- 传统建议是别重写；她要说的是**为什么你可能得考虑重写**，尤其是全新的「绿地」应用：
  - **大厂的巨型单体库**（她说 Meta、Google 这类）其实是「**为能力最弱的工程师设计的**」——用框架、约定、护栏、凭据限制去兜底；在 AI 出现之前，「AI 偷懒之前，我们先有人类偷懒」。
  - 真正危险的是**纯 vibe coding 出来的新项目**：「GrokBot 搭得极快」、人类基本不读代码、**没有任何护栏**，于是每个 agent 都用「当时最方便的方式」解题，日积月累代码库失控。她把这跟她发过一条推文的**有机建筑（organic architecture）**类比起来。
- 她的答案是先重构：**昨天算了一下，把整个 GrokBot 重构到 Dune 架构上，投入了 600 多个 PR**——正因为有了这批投入，才有今天早上自动合并的 20 个 PR。
- 「**我已经到了基本不再看代码的地步**」，她特意补了一句：这不是为了向你推销 token，而是为了说明达到这一步花掉了大量 token。
- PR 规模：大概**五十行到一千行不等，没有硬性上限**，但她鼓励 agent 把工作拆成多个 PR——理由是 git 历史是极好的上下文来源，原子化的 PR 更容易回滚、更容易定位是哪次改动引入了 bug。

## 八、Dune：把约束写进 CI，而不是写进规范

- **Dune** 是给 GrokBot 做的架构的代号，心智模型是「**Electron 应用的 Next.js**」，并且**专为让 agent 写代码而设计**。CI 很烦人，因为什么都查：
  - **禁用 useEffect**（React 最大的 footgun 之一），用了 CI 直接失败；
  - **禁用代码注释**——理由是「99% 的情况下 agent 写的代码注释只是在描述某些历史过程，跟代码完全无关」，她举的例子是：她随口说的一句「这个 PR 很烂，你应该改那部分」，最后变成了一条代码注释。agent 听讲者的话会过度当真。
  - **进程边界硬隔离**：Electron 里渲染线程要保证 60fps，每帧必须在 **16 ms** 内画完；因为隔离做得不好，常常把重计算/重 IO 意外拉进渲染线程 → 掉帧、卡顿。所以 GrokBot 里直接有 `ElectronMain` 和 `ElectronRenderer` 两个目录，并用 **import CI 检查依赖图**，禁止跨层/跨进程 import，由 CI 强制。
  - **Feature 共置**：feature / entry points / transcript cards（聊天里看到的那些卡片）是框架里的「名词」，创建方式非常固定，**一个功能的所有代码都在同一个目录里**——「它是为最笨的 agent 设计的，你根本不用思考」。
- **这一节的核心原则一句话：「最短的路径就是最好的路径。」** 因为 agent 天生爱走捷径，那就让那条捷径恰好是正确解法。
- **五层执行强度（从强到弱）**：① 代码库本身（架构/目录/禁止的依赖，最强，因为 agent 最爱复制现有模式）→ ② 静态分析：CI 检查、lint（针对观察到过的糟糕模式）、编译期诊断 → ③ Rules 和 BugBot（AI review，**软**，agent 可能忘记或执行不一致）→ ④ 技能 → ⑤ 风格指南/代码分割指南（最软）。
  - 她的告诫：**不要把软的那几层当成唯一的执行来源**，「如果你只有 rules、BugBot、技能和代码分割指南，那你的代码库变得一团糟只是时间问题」。要投资那些**难但强制**的东西。
  - 类比 Rust 的东山再起：严格的编译器 + borrow checker，「只要你的 agent 不写 unsafe block，代码能编译，它大概率就能跑、质量也不错」——编译器给了你不亲自 review 的信心。
  - **最糟的状态是靠人 enforce**：每当你在 PR 上写下「你不应该这样做」，都应该把它当成一种**代码异味**——「与其让我在 PR 上评论，不如想想怎么把它变成一条 lint 规则、怎么变成 CI 失败，或者干脆把这个问题彻底消掉」。
- 外部的话来说：**规范是软约束，架构才是硬边界。**（这句是我归纳时加的措辞，非原话）

## 九、Token 经济学：这是一道 ROI 题

- 「我在一个 AI 实验室工作，**那里有无限的 token**」，她明确说不是每个人都要照她的方式做，但对工程负责人和初创公司来说这是一道 ROI 题：
  - 前置投入确实烧 token（重构代码库尤其贵）；
  - 但你得以保持精简，**不想变成 Meta 那种一万人的工程组织**（巨大的管理与规划负担）；
  - 关键在于这笔钱买的是**以前做不到的事**——一个人想在代码库里落地这种级别的约束，以前要花好几年。
  - 回报不止于她本人：PM、设计师、GTM 也能安全地给 GrokBot 加功能。
- 顺带一条产品信息：**当天发布了 Grok 4.6**，很聪明、基准很好，且**每 token 成本与 4.5 相同**；「这是 Cursor 和 SpaceXAI 真正想优化的地方——**成本与智能之间的帕累托前沿**」，不是造最大的模型，而是找到「够聪明、但推理成本不高」的那个甜点。

## 十、收尾：给非技术人员的那一半

- 在 GrokBot 之前，「**Cursor 只有 Cursor**」——只有 agent window、CLI 和 IDE，都是**高级用户工具、以开发者为中心**；GTM/产品同事也可能在用，但体验并不愉快。
- 「**GrokBot 基本上就是非技术人员的 Cursor 时刻**」：界面像 iMessage，熟悉且好上手，很有趣；你可以给每个 agent 起好玩的名字，**每个 agent 就像一个有身份的人**，可以很自然地进行编排——每个账户对应一个 agent，PM 可以有个 agent 专门总结「Lauren 昨晚做的所有工作」。
- 一个她觉得挺说明问题的现象：PM 们现在也在提代码了——「这里有个 bug，我修好了，你能看一下吗」，她 review 完盖章。她的判断是：**这说明 Dune 架构撑得住**——正是这些严格的约束，让非工程专业的人也能高水平贡献。
