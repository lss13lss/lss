## 开场：为什么聊 Jev

今天我们来讲清楚：为什么 Jev 不值得那么关注。以及更重要的问题——每当有这样一个新技术的时候，我们怎么样判断：它究竟是下一个技术范式，值得我们关注和重点投入；还是它其实只不过是一个泡沫、一个 hype、一个过度的关注。

大家如果回忆的话，过去两三年，AI 圈有各种各样这样的概念：上一个"小龙虾"（OpenClaw）、MCP、RAG、LangChain、**Fine-tune（推测）**等等等等。所有的这些概念，我们都是带着时间戳、旗帜鲜明地在它刚出的时候就直接反对它，说它们虽然现在得到那么多关注、那么多大佬去说这个东西是多么重要，但是我们断定它一定会凉，大家不值得关注。而像 Agent、Claude Code、Skill 这样的技术范式，我们也是在第一时间就呼吁大家去紧密关注它，因为它真的很重要。

比如说在 2025 年的 2 月份，那个时候 Anthropic 内部还没有关注 Claude Code、所有人注意力都集中在 3.7 模型上的时候，我们就跟大家说，Claude Code 其实是一个非常非常值得关注的技术范式。那之后的发展也看到了：可能过了半年，大家开始疯狂地吹捧 Claude Code，很多自媒体博主也因为讲 Claude Code 而蹿红。但如果你一直关注我们的文章、关注我们的社区的话，你早就看到了这一点——你既不会在错误的技术上浪费时间和注意力，也会在正确的技术上加大投入。

这个视频我就先把这套方法完整地交给大家，并跟大家讲清楚为什么会产生这样的 hype。以后你再看到类似的叙事框架，一眼就能看出来它的 hype 机制到底是怎么产生的，这非常有助于你提升判断力。

在这里我还有一个请求：如果你只是想来杠一下，不打算看我的视频就直接杠的话，请你直接离开——我不需要你带来的流量和关注，我也懒得跟你解释。如果你看完了视频觉得我哪里说得不对，我非常愿意跟你讨论。

## 核心方法：判断新技术的五层框架

我们先说最重点：怎么用一件事情去判断这个新技术好还是不好？最重要的那件事，就是看它到底应该跟什么去比较。

比如说 Jev 这个技术，在它自己的叙事框架里，它是跟现在的大语言模型、跟这个 Frontier 大语言模型去比较的，然后通过比较得出"它速度更快、成本更低"。这就好像**帅Serious（推测，音"邵埃伦"）**去跟马斯克比较有没有薄肌一样——你找一个维度当然是可以比的，但问题是：Jev 的竞争对手是 GPT-6 吗？不是。因为 Jev——你如果看它的机制和要做的事情——它是一个 prefill 的模型，是没有 autoregressive 机制的。所以那应该去比较吗？不应该。

我在这里就不说技术语言了（像以前一样，我的文章早就发到社区了，社区里有专门的技术语言和技术讨论，在视频里我尽量不用技术语言）。在这里你就知道：Jev 本身是一个非常简单、非常小的东西。这些东西如果你用本地的小模型，可以做到比 Jev 精度更高、一致性更好、速度更快、成本更低——当然可能不能在四个维度同时满足。但你这样一放就会发现：Jev 虽然不错，但它没有一个特别突出的亮点，也没有吊打其他替代方案，它就是一个泯然众人的解决方案而已。可是它的技术叙事把它拿去跟大语言模型比较它最擅长的事情，大家就觉得它好像很厉害。

这事听起来并不难，但为什么它会引起很多哪怕看上去很懂技术的人的错判呢？这就涉及到我们判断一个新技术的五层框架。我必须把这个五层拆解出来，大家才能看清楚这种叙事框架的陷阱到底在哪、为什么大家会陷入这个叙事陷阱里面。

这五层分别是：

1. **理解**：你看到一个新技术，先要理解这个新技术是什么。
2. **边界**：你要知道它适用的范围和不适用的范围是什么。
3. **评价标准**：你要有一个自己的比较框架——要在什么维度上衡量它好还是不好。
4. **对标对象**（最重要）：它到底应该跟什么技术去对标。技术出现总是为了做一件事——让**帅Serious**去跟马斯克比薄肌当然不合适。哪怕我们认为薄肌很重要，在薄肌这个维度下，他也可以去跟另一个健身博主比；他去跟马斯克比薄肌，我们都知道是碰瓷。但是到了技术上，我们就看不出这一点了。一会儿我会讲为什么大家看不出来——这还涉及一个很重要的点：脑补。尤其在中文圈，中文科技博主们特别喜欢脑补，观众似乎也特别吃这一套，我也不知道为什么，但我会把这个现象分析清楚。
5. **决策**：前四步做完以后，再决定这个东西对你到底有没有用、到底需不需要关注。

## 案例拆解：Jev 到底是什么

我们回到 Jev 本身，先用 Jev 做案例，回头再用别的东西做案例，帮大家看清楚这五步分别是怎么做的。

**第一层——它是什么。** 同样不用技术语言：Jev 做的事情是把你现在的状态给到模型，给它几个选项，它帮你生成这几个选项对应的概率，然后你就可以直接去做了。这个技术的抽象其实是一个 if-else，或者说一个 case-when。**如果你用代码实现的话（推测，原音"Faco"）**：给一个 input，输出一些 output，并给出这些 output 的不同概率。想做到这个计算其实有很多方法：比如最近的 autoregressive 模型之前的 BERT；比如我们 GPT 加一个 JSON Mode；比如我们可以用本地小模型直接去读 logits 然后归一化——全都可以做到这件事情。Jev 只是这些手段的其中之一。这是理解它的技术本质。

**第二层——适用边界。** Jev 本身也讲了它什么地方适用、什么地方不适用：它在这种很短的、需要直接回答的地方用得比较好。

**第三层——评价标准。** 针对这样一个技术（我们可以把它叫做 AI referee / AI 裁判），我们一般从四个角度衡量：

1. **判断质量**——判得准不准，Precision、Recall 这些东西；
2. **延迟**——快不快；
3. **一致性**——每次给它相同的东西是否稳定，同样的输入能否得到同样的输出。因为我们要**判断工单（推测，原音"公单"）**，在它的使用场景下是需要可复现的；
4. **可校准**——当结果不像我们想象的那样时，能不能有效地校准。

当然在技术之外还可以评估成本，但成本是不断下降的，所以我们经常先评估技术好不好，成本单独看。

**第四层——真正的对标对象。** 订立好标准之后，再看它的 alternative。Jev 拿去跟 GPT 比较，但我们这里看到：完成这个任务，真正的 alternative 是什么？有好多个。甚至网上有段子：我其实有一个 **Python 自带的（推测，原音"拍像"）**类似 Jev 的东西，叫 random——我生成一个随机数直接去分布，做的和 Jev 差不多。这个时候在质量和一致性上比较，会发现 Jev 在很多任务上和 random 没有质变，质量上没有吊打 random，那就和猜差不多——这种情况下它到底有多有用，就非常值得商榷了。

而在这么多种技术路径里也能看到：用一个本地小模型去读 logits、做归一化处理，在刚刚说的四个维度下都是很好的。而且它有一个额外的好处：Jev 是自己的服务，要用云端，是一个网络服务——你给自己的系统平添了一个外部组件，而且这个外部组件你还看不透（黑盒）、不可以调；但你本地的小模型既是自己的，还可以调。所以很多地方，Jev 都被其他 solution 吊打，而且它也没有什么新意。

这时候就可以得出判断：Jev 不值得我们学习，不值得花这么多时间去关注它。

## Hype 是怎么产生的：三个成因

可为什么中文网络就产生了这样的热潮呢？这是视频第二个点：一个 hype 到底是怎么产生的。大家注意，Jev 本身的网站其实做得非常好，它的 marketing 那些东西我们都不说——那些都是 technics。我们要研究的是 hype 产生的本质机制，以及为什么过去很多东西都会产生这样的事。

**成因一：聪明的比较对象 + 打开想象力的叙事。** Jev 很聪明，把自己跟 GPT 去比较，而且比较的维度是大家需要的——成本、速度。因为很多人开始用 agents 以后，发现自己需要在这方面优化，而很多人不知道提升速度和降低成本的方法（比如用本地小模型的 logits 加归一化，大家是不知道的），所以它告诉了大家一个新的、不知道的东西。它还有一个不一样的范式叙事：大语言模型是针对人类做 RLHF（reinforcement learning with human feedback）的，而它自己是针对机器优化的。这个叙事打开了大家的想象力，大家马上开始脑补：这是一个新的技术范式！确实针对人类好像不行，未来会有一个 AI 对 AI 的世界，不需要让人看得懂的东西了——注意，这都是大家脑补出来的。

这个叙事为什么不成立？因为所谓的 Machine Native 的世界——不针对人优化、针对机器优化——就是过去二三十年所有软件、所有程序所做的事：你的程序不就是跟机器说的嘛，不就是给机器看的嘛，所有函数都是对着机器、不是对着人的。机器和机器之间的交流，本身就是通过数据、通过所谓 Machine Native 最优化的方式在进行了。把大语言模型和机器结合——所有的 agents 不都在做这件事吗？包括各种替代方案，也都在做这件事。Jev 并没有在这件事上往前多做多少，也没有提出什么全新的技术范式。可是因为它的叙事，大家直接掉进去了，对它的叙事框架本身不再质疑。

**成因二：叙事天然有利于传播，并被"懂技术"的博主强化。** 绝大多数技术博主在这里面起了推波助澜的作用：他们其实没有第三层和第四层的能力——没办法找到 best alternative，因为见得不够多。他们有能力看到 Jev 以后去读论文、看原文，甚至自己 implement 一下、试用一下——能做好第一步和第二步，首先这已经很难了，大多数人做不到这一步。可问题是，当你做了第一、二步但没有第三、四步的时候，你就陷入了它的叙事陷阱：你觉得它说的东西是真的，或有一定夸大但总体成立，于是你顺着它的叙事逻辑往下说——你就在它的叙事框架里面。这时候你还会产生一种虚妄：这个技术范式别人没看，我去看了，我看懂了——于是你变成了它整个叙事框架的传播者。再叠加一层：过去那么多 AI 技术能传播到我们面前，一定是符合一定的时代特征、符合一定的人性——我们需要这个叙事框架，所以这种叙事天然有利于传播。一个技术博主去讲这件事，内容天然会被流量放大。所以一段时间内我们会看到所有人都在吹"小龙虾"，不吹的人就看不见了——因为大家那个时候就想听这种叙事。这样的内容叠加上流量的分发机制，会不断轰炸我们。

**成因三：反对的声音会被误伤、被淹没。** 你做了第三、四层，和完全没做第一、二层的人，得到的结论很可能是一样的：一个完全不学习、固执的人也会说"Jev 不值得关注"。做了第一、二层的人会说：你这个人没有学习就去否定这个技术，没看懂叙事就去否定叙事，不合理，你是个草包。但看懂第三、四层的人说"我既懂它的技术、又看懂它的叙事，得出结论它不值得关注"时——第一、二层的人听到结论就已经不想听你说话了，没有注意力听你为何这么觉得。第三、四层的人也很容易成为被攻击的对象。比如我去年发的剖析 MCP 是什么、MCP 的短板、为什么它不是一个稳定的技术框架、一定会有新框架的那个视频，下面就有人直接说"我想把你收藏进 **shit list（推测，原音 Shabelis）**"，给了一堆似是而非的攻击——因为他觉得他是第一、二层，觉得我是第零层，他根本拒绝承认我可能知道第一、二层的东西、是从第三、四层去否定这件事的。

这就是 hype 的第三个成因，它会导致很多懂的人——比如**田渊栋（推测，原音"田园洞"）**——明知道 Jev 不好，但只会站出来说"没必要"。因为他说了以后还会受很多误解，又没有时间像我一样把这事完全解释清楚。于是很长一段时间，大家听到的都是对 Jev 的肯定声音。本来心智不坚的人看到这些东西，又不知道为什么不应该关注的时候，就无脑跟进去了——就像之前无脑跟"小龙虾"，可能采用 RAG、LangChain、Fine-tune 这样投入很多错误的时间精力。这对企业的管理层尤其是致命的。

## 运用：这套方法怎么看 MCP、LangChain、小龙虾

最重要的是找到它真正应该比较的对象。

- **MCP**：我们先想清楚它的机制和机制短板——把所有该确定性的东西 pass in 到 context 里面，非常不利于 debug，也非常不利于稳定地操纵电脑；这个东西就应该确定性地调用。所以 Skill 最后很好地弥补了这一点——我们说 Skill 可以很好地取代 MCP。
- **LangChain**：我们文章里讲清楚了，为什么过去学计算机先学 framework，但在 AI 里不应该先学 framework——背后是一个 design philosophy，我们不应该无脑继承。因为 AI 变得太快、底层不稳，用一个 framework 在上面，是把简单的东西搞复杂，非常不利于开发。
- **小龙虾（OpenClaw）**：因为它的黑盒机制和对话窗口，天然导致它在复杂任务、长线任务、或想调用 memory 的时候一定会有各种各样的问题；它的玩法也非常不适合普通人——该有的脚手架其实是没有的。第三个问题是过程的可观测性：把简单任务交给 AI，它直接做完了，不需要观测任何东西；但稍复杂一点，你就会想它到底在干嘛——是鬼打墙了，还是在反复思考、不断尝试新方案？调用了什么工具、改了什么文件、出了什么错？这些都很重要，尤其涉及你的关键技术资产或知识资产的时候。在专业的 AI 工具里，这些改动都是可见、可控制的；但在聊天软件里，你看到的只是一个"正在输入"或一个小动画。这个问题在越复杂的任务上越严重——复杂任务上你等的不光是一个答案，等的是整个过程，而过程在聊天窗里很难可见。

而且每一次讲的时候，我们都提出了真正有效的 alternative：比如小龙虾，当时**鸭哥（推测，原音"雅各/鸭哥"）**就直接开发了一个 OpenCode，还开发了对应的 iOS 客户端和安卓客户端——你用我们的 OpenCode，就是比小龙虾更好的 alternative，那个开发其实也不是很复杂。在 MCP、LangChain、RAG、Fine-tune 的过程中，我们都是深度使用、尝试了这个技术，拿出了评价框架，拿出了更好的 alternative，并且给大家讲清楚为什么大家天然觉得它好——它自带的叙事框架为什么吸引人、为什么这个叙事框架其实是错误的。感兴趣的话，当时的具体技术判断和五层方法的应用，都写在社区文章里，欢迎直接去社区看。

## 尾声：第四层很难，以及怎么把判断力教出去

想清楚这些事后，我发现有两件事很难弥补、但我们想尽可能弥补。第四层非常非常吃功力：我可能做到第一、二层，也许在 AI 帮助下能做到第三层，但很难做到第四层——因为吃过见过，你才知道什么东西重要；真的知道其他 alternative，才能找到 alternative；真的知道 Jev 应该跟什么比较、小龙虾应该跟什么比较，才能找到那个东西。而且最好你还能把它实现出来，证明你说的是真的。比如鸭哥对比小龙虾时真的做了一个 OpenCode，大家用了发现就是比小龙虾好用，才知道你说的是真的——不然空口无凭，你可能想的也是错的，或者做出来才发现不是那么回事、没理解清楚技术范式本身。这是鸭哥的功力，是我不具备的东西。

而我们想把这个交给学员的时候也很难，因为背后是很大的基本功和很多实践。鸭哥每当有新技术，天然就想去尝试、去思考、去跟脑子里所有知识对比。这件事如果我们不教方法、直接给结论——"Jev 不值得关注"——反而会让学员显得像个**二逼（推测，原音"耳鼻"）**：身边所有人都说"Jev 好棒、是下一个技术范式"，他去说"Jev 不值得关注，给你看鸭哥的文章"——第一，别人不会去看；第二，别人会觉得他是站在第零层的人。

那怎么办呢？今年年底课程刷新的时候（鸭哥正好也 **gap 回来了（推测，原音 Gav）**，4 月到 10 月正在干），我们会专门把这部分"复杂化"——之前我们想方设法简单化：告诉大家正确答案和背后的原因就行了。现在我们可能会先教大家怎么做出一个更好的 Jev（鸭哥已经做了：用很多本地模型做归一化、做测试）。你做了以后，可以先顺着叙事去讲，不需要站在一个非常清醒的高度告诉大家"你们都是错的"；你可以说"大家说得对，Jev 确实很重要，但我给你一个更好用的 Jev，我们来比较——它就是更好用"。这件事我们都可以教给大家。与此同时，当你通过这种方式取得信任以后，你可以再说：其实这件事也不是那么重要，我们去做更重要的事吧。有了前面大家对你技术的了解和信任，你说话会更有分量，这时候再想做什么改变也更容易——而不是坐在那边批判大家。坐在旁边批判大家的人，一般在公司里是不太受喜欢的。
