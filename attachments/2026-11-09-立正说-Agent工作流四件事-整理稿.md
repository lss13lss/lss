## 一、主论点：AI 用得好，靠的不是复杂概念

开场就给了全部结论——"我试图两分钟跟你讲清楚这个事是怎么做的"：

> **AI 用得好，绝对不是用复杂的概念。现在所有 Harness 的文件工作、上下文工作，Markdown 加 Search 98% 都能解决。**

（这句被明确归给"鸭哥"，后文又称"鸭哥特笃定地说出这样一句话"。）

配套的方法是**先有简单框架，再往上搭**："这个理念就是……一定 [是用] simple 的东西去把这个东西做好，这样才最有效，然后它才最能往上走。"

值得注意的是他给的时间感：这段工作流"我们现实都觉得这个东西太简单了，一句 [话] 不需要出 [视频]"。**越有效的方法，越不像是可以拿来讲的方法。**

## 二、四件事

> "我刚刚跟你所说的、所用到的事，无非就四件事。"

| # | 事情 | 一句话 |
|---|---|---|
| 1 | 选一个 agent 工具 | 能读本地文件、能操作工具（Claude Code / Codex / Cursor） |
| 2 | Document First | 所有工作留成本地文件，用文件夹管上下文，做好索引 |
| 3 | 接通邮件 | 让 agent 读邮件、按索引路由到资料、自己判断要做什么 |
| 4 | 凭证交接 | 账号密码用 1Password 之类的方式安全传递 |

### 2.1 第一件：工具只要能读本地文件、能操作工具

"你无论是用 Claude Code、Codex、Cursor……国内我不知道，[WorkBuddy] 也许行，我不知道行不行，应该可以。就用一个 agent 工具，反正能操作、能读你的本地文件、能去操作工具的这样一个工具。"

判断标准只有两条：**能读本地文件** + **能调用工具**。不涉及具体品牌。

### 2.2 第二件：Document First（这一件是整套方法的地基）

- 工作做完以后，**一定留成本地的文件**；
- 需要别人看，就**上传到 GitHub**，分享出去别人的 agent 也能读；
- 用**文件夹**的方式管理上下文；
- 文件夹乱了，就让 agent 去整理；
- **索引就是你的 `AGENTS.md`**；
- 每个文件夹还可以让 agent 再生成一个 `index.md`，说明"这里边有什么"，方便未来 AI 看。

最后是一条可以每天照念的**习惯指令**：

> "每当你做完什么东西以后，你就说这句话就行了：**把该存的文件存一存，该更新的索引更新一下。**这样的话你工作就可以一直留下复利。"

### 2.3 第三件：用邮件做 agent 之间的交接

两种做法，从手动到自动：

- **手动**："我今天看到鸭哥给我发了一个邮件，然后我就跟我的 Codex 说：你去读一下他的邮件，要做的事做一做。"——"是真的就说这句话。"
- **自动**：给一个 hook，"比如说我收到了来自谁谁的邮件，你就看一下有什么工作，给我的 agents 做一下"。

**背后的原理**（他认为这才是重点，不是操作步骤）：

1. `AGENTS.md` 知道我的所有文件在哪；
2. agent 已经 connect 了 Gmail（通过 plugin，或通过他们发的 skill）；
3. agent 读完邮件后，**经过自己的 `AGENTS.md` 路由到对应的文件**；
4. 于是它自己就能想清楚要干什么，然后把事干了。

### 2.4 第四件：凭证怎么安全交接

有些事必须分享账号密码。"你可以问 Codex 说：我想给另外一个人发邮件、分享我的账号密码，怎么样可以安全地去做这件事？它应该也有方式可以告诉你怎么做。"

在实际协作里他们用的是 **1Password**：对方开好权限、做好设置，"然后 1Password 传给我，然后我的 AI 读那个 1Password，然后去用上。"

## 三、邮件是他们真正的协作界面

（02:16–03:40）

> "我们非常注重邮件交流。尤其是我们邮件一般会写一个**给人看的版本**和一个**给 agents 看的版本**。"

触发场景很具体：后台权限变更（有人退课、有人切换权限）、客服问题、推动平台合作方做事、以及"我做一个软件，需要鸭哥在 Logto 这类 SaaS 里给我开一个登录权限"。

流程是：**我的 AI 先做好 → 发邮件给他 → 他的 agent 看完再发邮件给我 → 协作完成**。

结论是最反直觉的一句：

> "很多时候我们做很多协作的工作，**但是我们之间的交流并不多**，因为就直接靠 agents 和邮件的方式去做就好了。除非很急的东西，我们会 message 或者打电话说一下。"

## 四、内容生产：观点归人，写作归 AI

（00:45–01:35）

被问到"你们的内容是 AI 写的吗"，他拆成两部分：

- **"首先我的绝大多数内容都是我自己的东西，然后 AI 加工。"**
- 为什么愿意让 AI 加工：**它把门槛整体降下来了**——"包括心理门槛、发布门槛等等，降低了很多"。
- 取舍很清楚：**"我不是特别在意我的写作，我特别在意我的观点，或者说我的思想。所以说保证这个思想是我的，但是写作呢……"** 他知道自己写传播效果可能更好，但更希望把观点更多地表达出去。
- 理由是带宽："我有太多想法和观点，但是我的 bandwidth 是有限的，所以我要提高这个带宽，于是我就 [在] AI 的帮助之下去发东西。"

**具体到当天的例子**（这段最能说明"工作流"和"工具"的区别）：播客刚录完，他马上去找老婆吃饭；同时 AI 帮他**剪辑、加字幕、转成伴读文章**，"所以今天晚上它应该就可以在社区里边变成一个伴读文章发出来"。

## 五、对照案例：鸭哥的 deep news（全自动量产 + 手写稀缺）

（01:36–02:10）

- **自动化的那一半**：deep news 每天出 2–3 篇最前沿科技的观察、解读与分析（包括对 **Jev** 的分析）。这是"他和 AI 的一个完整工作流"——AI 到处扫描、用他的历史文章和观点做校正与反馈，然后给他看；他每天看大概 20 篇，对其中几篇提建议，最后发出 2–3 篇。
- **手写的那一半**：他坚持手写一些东西，但"每次可能要等好几个月"才能看到一篇；质量非常高；"每次他发一个手写文章，大家就会买很多课"。

> 这个对照值得单独记住：**自动化负责产量与覆盖，手写负责信任与转化。**两者不是替代关系，是分工。

## 六、Personal Agent 是 Codex 的子集

（06:07–07:10）

- "现在硅谷炒得特别火的 personal agent，其实在 Codex 就可以解决了。**Personal agent 是 Codex 一个子集。**"
- 差别在**资源边界**：personal agent 是一台云端电脑，"它的权限和它的文件是受限的"；而 Codex 这边"你有很多本地的文件，你有无限的资料"。
- 代价是 Codex "有一个门槛，就是你最好有一个自己的电脑"。
- 能力差别："personal agent 很多不能干的事情，Codex 能干。"

**他举的实例（短视频剪辑全流程）**：平时在外面用手机录 → 放进 iCloud 的 shared album → Codex 有一个工作流去读这个 shared album → 自己剪辑 → 自己发布到 YouTube。"我要干的事情就是录一下、放到这个 shared album，然后它就发到我的 YouTube 上了。"

同一个任务用 Muse："理论上能干，但是我发现它要去干的时候就很麻烦"——要申请 shared album 的权限、要下载、下载文件大小又受限制、上传时又有很多问题。相比之下，"在电脑上，像 Codex、Claude Code 这样的工具，它的编程能力很强，computer use 能力很强，**理论上可以完成你能干的所有的事，包括点击各种页面**"。

## 七、两个必须打开的开关

（07:10–08:10，此段有屏幕演示）

1. **Computer use**——打开后"它就可以控制你的 native app 和 Google Chrome，都可以去拖拉拽地去干很多事情"。（演示中还涉及 macOS 的屏幕录制 / entire screen 权限。）
2. **Remote connection**——把手机加进去；手机上点开 Codex，"你就会看到你的 Codex 的所有 session，然后你就直接在上面远程控制就好了"。

## 八、国内现实与替代方案

（08:10–08:48）

- **主要障碍不是方法，是网络**："国内的问题是什么呢？是大多数人都连不上这个东西。就是方法论大家都知道，但是连不上，它的网络环境有问题。"
- 现状："所以基本上大家还是在用 UU 远程 [控制 Mac mini]。"——因为"Mac mini 才能一直开着，Mac 是不能一直开着的"，但"其实连得没有那么顺畅，可能是网络环境也有原因"。
- 另一个现实："国内的模型又不行了。"
- 替代选项：**Orca**——"它也是个开源的，而且免费可以用"。他看重的是它能养成一个**不依赖任何工具的习惯**：一个任务上半截交给 Codex、下半截交给 [另一个]，"它就可以帮你养成一个不依赖任何工具的习惯"。它还有手机端的远程控制，"可能用起来会好用"。
- 结尾："我觉得我给你发一下，如果大家感兴趣的话可以试试。"
