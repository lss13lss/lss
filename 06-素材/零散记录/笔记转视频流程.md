# 笔记转视频流程

先用一篇真实笔记跑通“母稿 → 素材 → 成片 → 发布 → 复盘”，再将重复而稳定的步骤自动化。一份母稿是共同事实来源，各平台版本分别调整呈现形式。

> [!info] 整理范围与状态
> 2026-09-21 合并两份 2026-04-03 旧稿：本页原先的网页工具建议，以及《自动化内容发布工作流设计》中的工程设计。二者均是方案，不代表已经部署、已购买工具或已获得自动发布授权。本次保留可复用流程、数据结构、实验与来源，移除重复推荐和无法追溯的引用标记；产品能力、价格、平台配额、规则均未重新核验。

## 一条内容先跑通五个环节

| 环节 | 输入与产出 | 完成标准 |
|---|---|---|
| 母稿 | 真实笔记 → 核心观点、3—5 个展开点、例子、来源、结尾 | 能说清发生了什么、AI 做了什么、结果与局限是什么；所有平台共用事实底稿 |
| 素材 | 自有照片、录屏、聊天截图；必要时授权素材或 AI 示意画面 | 素材能对应到脚本位置；记录来源、授权或生成信息；私人信息处理清楚 |
| 成片 | 脚本 → 镜头/分页、旁白、字幕、封面、导出文件 | 文字、声音、画面一致，手机可读；可编辑源文件与导出结果都留下 |
| 发布 | 审定的各平台版本 → 发布记录 | 核对当前平台格式与生成内容声明要求；发布后确认实际可见状态，保存链接或内容 ID |
| 复盘 | 制作记录与真实反馈 → 下次修改 | 区分事实数据、自己的解释与下一次要试的变化 |

实际平台顺序查 [[03-项目/账号运营/AI 账号定位|AI 账号定位]]，写作模板查 [[03-项目/账号运营/内容协作与多平台模板|内容协作与多平台模板]]。此页不另建一套账号策略。

## 最小的内容包

旧报告把它叫统一内容包（Canonical Content Package / CCP）：先整理平台无关的事实，再转成不同平台稿件。可以先用 Markdown 保存，不必为了这套概念新建服务。

```yaml
content_id: "填写稳定编号"
topic: "本次主题"
source_notes: []
core_point: "本次最想讲的一点"
audience: "本次目标读者"
facts_and_examples: []
sources: []
unknowns: []
tone: []
ending: "可选：读者问题或下一步"
assets:
  own_materials: []
  licensed_materials: []
  generated_materials: []
platform_versions: []
publication:
  status: "draft"
  target_platforms: []
  timezone: "Asia/Shanghai"
  schedule: null
```

旧报告的示例用了 `America/Toronto` 时区、“3 天解决拖了两周的报告”等虚构案例。这些只属于示例，本次不保留为用户经历或实际配置。

### 素材与成片需要留下什么

- 素材记录：原文件、来源 URL、授权凭证或使用范围、在脚本中的位置。
- 生成记录：使用的工具/模型、提示词、生成时间、选中结果；工具提供 seed 等参数时再记录，不假定所有工具都有。
- 成片记录：脚本、分镜或分页、字幕 SRT/VTT、音轨、封面、可编辑源文件与导出文件。
- 发布记录：使用的内容版本、平台、发布时间、发布 ID/链接、最终状态、可见性、失败原因。

旧稿的三个成片模板可作为起点：9:16 口播字幕、封面加图文轮播、旁白加过程画面。用真实素材不足时，再决定是否补通用素材或 AI 示意画面。

## 从人工流程扩展到自动化

只有制作与发布的重复步骤足够稳定时，才需要旧报告中的工程层。下列是可选设计，不是待办清单或已运行系统。

```mermaid
flowchart LR
  A[原始笔记] --> B[统一内容包]
  B --> C[平台稿与素材清单]
  C --> D[素材制作与渲染]
  D --> E[核对内容及当前平台要求]
  E --> F[审定稿与发布队列]
  F --> G[平台发布]
  G --> H[查询最终状态]
  H --> I[记录反馈与下次修改]
```

| 设计点 | 保留它的原因 |
|---|---|
| 平台适配器 | 将各平台的稿件格式、鉴权、上传、发布和状态查询分开；某个平台变动时只改相关部分 |
| 平台规则配置 | 记录内容类型、文字/媒体限制、字段、鉴权、配额、审核模型、核验日期和来源；具体数字以实施时官方文档为准 |
| 队列与任务状态 | 区分 draft、ready、publishing、published、failed；媒体生成和审核耗时可异步处理 |
| 幂等与重试 | 用稳定内容编号、平台和版本识别重复发布；遇到网络错误先查结果，再决定重试，避免一次内容被发多次 |
| 结果回读 | 上传成功、请求成功、审核通过、公开可见是不同状态，需要确认最终结果 |
| 日志与成本 | 记录输入版本、素材来源、生成版本、发布 ID、状态变化；成本按文本、图片、语音、视频和人工修改时间分别统计 |
| 暂停与恢复 | 支持停止排期、暂停单个平台；优先复用已经生成的成品。已公开发布的内容不保证能完整撤回，“回滚”不能代替发布前检查 |
| 权限与密钥 | 平台凭证留在专门配置或密钥管理中，稿件与日志不存密钥 |

旧报告提出 OpenClaw 编排、渲染 Worker、对象存储、数据库、队列、平台连接器，以及大规模时使用 Kubernetes。这里仅保留职责划分；本次没有核验 OpenClaw 的具体组件和接口，也没有理由仅因模型更强就立刻部署完整系统。小规模可以先用本地文件和人工发布完成同样的内容闭环。

旧报告还包含播客分发设想：单独生成音轨、节目说明和封面，并保存稳定单集 ID、音频 URL、文件长度与类型。若后续开展播客，再核对 RSS、托管与目标平台规范；当前不新增播客项目。

## 复盘字段与小实验

最小记录字段：主题、平台、形式、开头、素材类型、发布时间、制作耗时、实际反馈、解释、下次改法。将“事实数据”和“我的推断”分开。

旧稿提出的四组实验保留为选项，数量不是硬指标：

1. 同一篇笔记改成图文、30 秒口播、60 秒口播、长文，比较信息损失与制作成本。
2. 同一条脚本试自有素材、授权素材补充、AI 画面补充，比较真实感和可控性。
3. 同一内容尝试观点型与结果型封面，用实际反馈比较。
4. 在一个主题上持续制作若干条，观察流程是否更顺；旧稿建议 10 条，但没有证据说明这个数字适用于当前账号。

如果真正开发自动发布，再验证几种实际故障：文字/媒体超限、缺素材、鉴权失效、限流、上传后状态不明、重复请求、仅私密可见、生成费用超预算。先选目标平台，再写与它有关的测试，不把所有平台的假设一起实现。
