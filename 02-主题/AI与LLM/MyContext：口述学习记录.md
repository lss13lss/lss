### 一、口述中的疑问 × 阿里源码的答案

#### ① embedding 会不会把群聊消息、时间带进去？

**不会，阿里做了三层分离**（`kl-graph/kl_graph/ingest/loaders/`）：

| 层 | 时间用不用 | 证据 |
|---|---|---|
| 排序与切块判定 | ✅ 用 | `message_loader.py`：按会话分组、组内按时间排序，间隔 ≥3 小时判会话边界 |
| embedding 文本 | ❌ 不进 | 会话边界用字面 `SESSION_BREAK` 标记，源码注释原话：**"consumed/stripped during slicing (never stored, never embedded)"**——切块时剥离，永不存储、永不进向量 |
| 结构化元数据 | 存 payload 不进向量 | `_embed_chunks()`：sender/conversation 存向量库 payload，**用于检索过滤，不参与相似度** |

**重写版建议**：语义进向量、结构进 payload、时间只做边界判定，三层别混。

#### ② IM 消息短，"不涉及切 chunk"——方向反了

`kl-graph/kl_graph/ingest/chunker.py`：切块单位不是"消息"是**会话块**——3 小时空闲硬切一次，块内消息按时间序拼接，超过 token 预算再按句子软切（RAGFlow `naive_merge` 的忠实移植，tiktoken `cl100k_base`），**带 overlap**；文档/会议纪要走另一条字符预算 + 标题感知路径。**正因为单条消息短，才要靠会话块攒语境**。

#### ③ 索引机制（口述说"要着重记一下"）

阿里侧完整证据链：

1. 每条消息原始 JSON 进 `raw_records`（重放层）→ 规范化进 `messages`
2. 幂等索引 = `UNIQUE(channel_id, resource, external_id, payload_hash)` 四段键（`store/src/migrations/vault/v2-raw-normalized.ts:31`）——比口述说的"数据源+类型+ID"多一段 `payload_hash`，用于编辑/撤回更新与崩溃重跑
3. 检索结果**永远带 source references**（官方原则"Evidence before answers / 先有依据，再有答案"）
4. forge 的 `escapeHatches` 直接存**本人原话**（带出处）——生成时引用的是可回查证据，不是抽象摘要
5. Agent 不可用时搜索**明确降级**为本地排序结果，不静默编造

#### ④ 亲密度口径（口述自己说"概念有点乱"）

阿里 forge 的口径（`vendor/forge/forge/relations.py` + `signals.json`），可直接当定义用：

```python
total = from_w + to_w      # 双向加权量（你找他 + 他找你）
self_share = to_w / total  # 你主动的占比
```

- **不是窗口是半衰期**：`halfLifeDays = 90`、`floorWeight = 0.05`（近期权重高但永不归零）。重写版的"24 小时窗口"会把昨天的 A 档直接清零
- **双向占比，不是单向计数**："他发来的消息数"是纯入站量，只群发不打理你的人会拿高分
- **双门槛过阶梯**：A 档要 `minTotal=200` **且** `minSelfShare=0.25`；B 50/0.15；C 12/0.05；D 1/0
- **群聊封顶**：`groupOnlyCap = "C"`——"Being in a busy group with someone is not the same as being close to them"
- **敏感头衔强制 S 档**：`(hr|人力|人事|财务|法务|审计|合规|总监|总经理|vp|ceo|cto|coo|老板|董事)`；owner 手动调整**只能收紧不能放松**
- 半衰期锚点 = **语料最后一天而非 now()**（保确定性："same corpus + same signals ⇒ identical output"）

#### ⑤ "@你算他发的消息，你@回他算不算你的回复"

阿里不依赖 @ 符号，靠**时序窗口 + 最小长度**（`signals.json` 的 `responseGate`）：

| 参数 | 值 | 含义 |
|---|---|---|
| `replyWindowSeconds` | 10800（3 小时） | 超时不再算"对上一条的回复" |
| `minReplyCodepoints` | 4 | ≤3 个码点的"嗯/好/ok"不算回复，**顺便过滤纯表情** |
| `contextTurnsBack` | 4 | 回头看几轮配对 |
| `silenceWindowSeconds` | 86400 | 沉默要等 24h 后有后续活动佐证才算主动沉默 |

口述"他@你之后你立刻@他就算回复"的直觉与 `replyWindow` 同构，但阿里更宽容（3 小时）且不看形式。**表情回复、引用回复、@提醒的口径问题，靠"时序窗口+最小长度"统一定义比逐个适配回复形式更稳**。词法判定（genuineAsk / chitchatReply）在 locale pack（`forge/locales/zh-CN.json`），语言无关阈值在 `signals.json`——换语言只换词法包。

#### ⑥ 蒸馏时机（重写版定凌晨 3 点）

**阿里不定时，攒批**（`packages/knowledge-feed/src/auto-build.ts`）。建图全链路实测约 2 小时、其中 83 分钟是 embedding，且 Phase A 对已有向量**不做差集**——每来一条新消息就建图 = 每条烧 50 分钟向量化。触发条件三选一：

| 条件 | 值 |
|---|---|
| 首次（图没建过） | 立即 |
| 攒够条数 | **500 条** |
| 攒够时间 | **24h 且有新数据**（没新数据建图是纯浪费） |

外加：最短间隔 1h；**首次建图至少等 14 天跨度**（或学习范围取小）；失败指数退避 30m→1h→2h，**退避态只在内存**（用户修完配置重启即重试）。源码注释明确反对"距上次 N 分钟"纯节流：限频率不限总量，"按条数攒批才把成本与收益绑在一起"。

#### ⑦ 无实体时的降级（上下文+向量检索拟定答案）

方向与阿里一致 ✅，但注意阿里的措辞：**明确降级**（"不是悄悄生成没有依据的答案"）——降级要可观测，否则排查"这条回答为什么差"无从下手。

#### ⑧ 规则分档 + 大模型二次降档取最低

重写版：规则（亲密度）分档 → 模型判断信息够不够 → 取 min。

**阿里刻意不走这条路**：guard 是唯一决策点、纯规则零模型；"信息够不够"不问模型，问 forge 的测量元数据（`evidenceSufficient` / `coverage.replyShapes` / `riskDetectable` / `askKindDetectable`）；12 条降级**只降不升**（`reply:0 / handoff:1 / draft:2 / silent:3`）。模型唯一能"说不"的机会是 compose 返回 `text: null + noReplyReason`。

`signals.json` 顶部注释一句话说尽：**"The model never free-judges at build time; it only reads what these rules measured."**（模型在构建期从不自由判断，只读取规则测量出的结果。）理由是可复现性：规则两次跑全等，模型两次判断可能不同——而这决定"要不要以你的名义自动发消息"。

**"取 min"的精神与"只降不升"一致，保留**；建议把"信息够不够"从模型自由判断改成可测量的 coverage 检查（如：该类问题历史样本 ≥N、该收件人交互 ≥M 条）。

另注意：决策是**四态**不是三态——`reply / handoff / draft / silent`，口述漏了 **handoff（转交本人）**。`alwaysDraftKinds = ["decision_request", "approval_or_commit"]` 硬编码：被要求**决策/审批/承诺**时永不自动回复，与蒸馏结果无关（"a rate is evidence, not permission"）。

#### ⑨ 图谱不抽人-人关系边、用会话作边

重写版的简化合理，但要看清阿里是**双轨制**：图谱（kl-graph，LLM 抽实体/事实/关系）只服务**检索问答**；亲密度分档（forge，纯统计）完全不依赖图谱。**两个关注点分开：语义关系归图谱，交互强度归统计**。如果会话边同时承担两个职责，后面会挤在一起。

#### ⑩ 两分钟增量拉取 + 手动 CLI 补拉

重写版缺一道阿里有的防线：**发送前 freshness 判据**——`sync_cursors.watermark` 滞后 > `maxLagSeconds = 150`（2 分钟兜底 + 余量）**或滞后未知**，都判 stale **不发送**。源码注释："取不到就报 None（未知），绝不报 0。把未知当 0，与「完全同步」在最需要区分的那一刻长得一模一样，而那一刻之后消息已经发出去了。"——手动补拉失败/仍滞后时，宁可 stale 不回，也不拿旧数据以本人身份回过时的话。

#### ⑪ 蒸馏卡的 ≥5 规则

对应阿里 `verification`：`minSupport = 8` **且** `minDistinctDays = 4`（还要 `minScenes = 2`）。注释："Prevents 'anything a polite colleague does' from being published as personality"，且双门槛必须同时满足——"minSupport alone accepts one busy afternoon, minDistinctDays alone accepts one message a day for four days. **Neither is a habit.**" 重写版的"≥5"是单维计数，一次热闹的故障复盘下午就能造出失真蒸馏卡，建议抄双门槛。

另：forge 最终产物不是 JSON 而是**可执行的 Agent Skill**（`SKILL.md` + `rules.json` + `style.md`），且测量（`features.json` 原始率）与政策（`rules.json` 结论）分文件发布，host 可复核。
