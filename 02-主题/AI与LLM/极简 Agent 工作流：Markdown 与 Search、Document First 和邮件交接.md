# 极简 Agent 工作流：Markdown 与 Search、Document First 和邮件交接

> [!abstract] 一句话
> 把上下文做成**文件系统**（markdown）、把检索交给 **search**、把路由交给 **AGENTS.md**、把交接交给**邮件**——四件事就够了。真正让 agent 干活的不是 prompt 技巧，而是**它能不能找到资料、理解任务、接上前一个人的工作**。

## 一、论点：有效的方法通常简单到"不值得讲"

> "AI 用得好，绝对不是用复杂的概念。现在所有 Harness 的文件工作、上下文工作，**Markdown 加 Search 98% 都能解决**。"

他补了一句时间感：这套东西"我们现实都觉得太简单了，一句话不需要出视频"。

这句话我认为是本期最值得记的**元信息**：**方法的价值密度和它的可讲述性成反比**。复杂的工作流容易被讲成课，因为它有步骤、有名词、有对比图；而"把文件存好、索引更新、让 agent 去读"没有可表演的结构——但它在 90% 的场景里就是全部。

## 二、四件事，及其"最小实现"

| # | 事情 | 判断标准 | 最小实现 |
|---|---|---|---|
| 1 | 一个 agent 工具 | **能读本地文件 + 能调用工具** | Claude Code / Codex / Cursor 任选，不绑品牌 |
| 2 | Document First | 工作有无留下**可被再次读取的文件** | 本地文件夹 + `AGENTS.md` + 每目录 `index.md` |
| 3 | 接通邮件 | agent 能否**自主接收任务** | Gmail connect（plugin 或 skill）+ 一句 hook |
| 4 | 凭证交接 | 权限能否**安全地跨人传递** | 1Password 共享，由 agent 读取 |

第三、四件是可选的进阶，**前两件是地基**。地基没打好，第三件只会让 agent 更快地做错事。

## 三、Document First 才是真正的地基

他把这件事拆成三层，我认为层次很准：

**第一层：文件。**"你所有的这些工作，做完了以后你要留成本地的文件。"需要给别人看就推到 GitHub，"别人的 agent 也是能看的"。

**第二层：索引。**"索引就是你的 `AGENTS.md`"，每个文件夹再让 agent 生成一个 `index.md` 说明"这里边有什么"。

**第三层：习惯。**一句可以每天照念的指令——

> "**把该存的文件存一存，该更新的索引更新一下。**这样的话你工作就可以一直留下复利。"

这三层里，我认为**第二层是最容易被做错、也最容易被跳过的一层**。`AGENTS.md` 不是一篇介绍文档，它是**路由表**：agent 收到一个任务时，靠它判断"这件事的资料在哪、该改哪个文件、有什么约束"。文档写给人看，路由表写给机器查——两者混在一起写，就会变成一篇谁也不读的说明。

三层的关系是**互相兜底**的：只有 markdown 没有索引 → agent 知道有资料但找不到；只有索引没有 markdown → 索引本身变成新的表演。**"Markdown + Search 98%" 这句话成立的前提，是这三层都在。**

## 四、邮件作为 agent 之间的协议

这是我在这期里学到的、最不像"技巧"的一点。

他们的做法：

- 邮件写**两个版本**：给人看的版本 + 给 agent 看的版本；
- 我的 AI 先做好 → 发邮件给对方 → 对方的 agent 读完再回邮件 → 协作完成；
- 只在很急的时候才用 message 或电话。

为什么邮件合适？我从他们的做法里反推出三个性质：

1. **异步**——不需要两个人同时在线，agent 可以在任意时间点接续；
2. **可审计**——有主题、有正文、有收发记录，天然就是任务单；
3. **有身份边界**——谁发的、发给谁，权限关系写在协议里。

聊天窗口三者都不具备：它是同步的、上下文一滚就没了、而且没有明确的"这一条是任务，那一条只是寒暄"的边界。**把 agent 之间的交接放在聊天里，等于让它每天重新猜一次意图。**

配合的凭证方案是 1Password：对方开好权限 → 1Password 传过来 → 我的 AI 读 1Password → 用上。这里有个隐含要求：**凭证只能"被读取"，不能"被写进上下文"**，否则交接链路本身就成了泄漏面。

## 五、Personal Agent 是本地 harness 的子集

他的判断很直接：**"Personal agent 是 Codex 一个子集。"**

差别不在智能，在**资源边界**：

| | 云端 personal agent | 本地 harness |
|---|---|---|
| 文件 | 受限于云端那台机器 | 本地全部文件、"无限的资料" |
| 权限 | 受限，需要逐项申请 | 你有的它基本都有 |
| 门槛 | 打开就能用 | **你得有一台自己的电脑** |

他举的例子很有说服力：手机录短视频 → 丢进 iCloud shared album → Codex 读 shared album → 自动剪辑 → 自动发 YouTube。同一个任务用 Muse，"理论上能干"，实际要申请相册权限、要下载、下载有大小限制、上传又出问题——**每一步都是一次权限谈判**。

结论可以压缩成一句：**agent 的能力上限，等于它能触达的资源边界，而不是模型的分数。**

## 六、两个必须打开的开关

1. **Computer use**：打开后可以控制 native app 与 Chrome，"拖拉拽地去干很多事情"。
2. **Remote connection**：手机端能看到本机所有 session 并远程控制。

第二条的意义常被低估：它把"用 agent"从**坐在电脑前**变成**随时随地派活**。视频里的用法是躺在床上的时候、聊天的时候、开车的时候让它干活——这其实是在把 agent 变成一种**异步劳动力**，而不是一个需要你陪着的工具。

## 七、国内约束：卡住的不是方法，是网络

他的判断很坦诚：

- "方法论大家都知道，但是连不上，它的网络环境有问题。"
- 现状是"大家还是在用 UU 远程控制 Mac mini"——因为 Mac mini 能一直开着，Mac 不能；但"连得没有那么顺畅"。
- 另一个现实是"国内的模型又不行了"。
- 替代方案是 **Orca**（开源、免费、有手机端），他看重的是它能让人养成**不依赖任何工具的习惯**：一个任务上半截交给一个 agent、下半截交给另一个。

这一段的真正信息不是产品名，而是：**在受限环境里，最优解不是找到"能用的那个工具"，而是先把自己变成"不依赖某个工具的人"**——上下文在本地、索引在本地、习惯在本地，换工具只是换执行器。

## 八、这套方法与本库现状的对照（助手观察）

看这期时我一直在对照你现在的 vault 实践，结论是：**四件事里你已经做了两件半，缺的是第三和第四件。**

| 视频里的要求 | 本库现状 | 缺口 |
|---|---|---|
| 一个能读本地文件的 agent | 已有（本机 agent 直接读写 vault） | — |
| 文件沉淀 | `attachments/` 三件套命名规范已成惯例 | — |
| `AGENTS.md` 路由表 | vault 根目录有 `AGENTS.md`，另有 `02-主题导航.md`、`06-素材/视频转写素材索引.md` | **索引靠手工追加，没有"重建/校验"动作**，长期会腐化 |
| 每目录 `index.md` | 只有顶层导航页 | 主题子目录没有各自的入口 |
| 邮件交接 | 邮箱连接可用（agent-mail） | **未接入日常工作流**，目前只是通讯工具 |
| 凭证交接 | 现在靠本地 overlay 文件隔离 | 没有 1Password 式的跨人传递路径 |

最值得马上补的一条不是邮件，而是**索引的自动重建**：现在的导航页和素材索引都是我在每次新增后手工追加，一旦某次漏了，agent 的"路由"就开始出错——而这恰好是这套方法里唯一不能靠"记得做"来保证的环节。

## 九、我认为需要打折的地方（助手独立判断）

1. **"98%"是口头判断，没有任何评测口径。** 多少任务、什么类型、什么算失败，全部缺失。它更像是"我用了两年没遇到需要更复杂方案的情况"，而不是统计结论。
2. **"我们之间的交流并不多"是双人小团队的实况。** 两个人、高信任、共享同一套上下文、目标完全一致——这是最容易让协议生效的条件。放到多人组织里，邮件协议会立刻退化：邮件变成抄送链、变成留痕、变成"我已同步"的证据。**换句话说，它会长成另一种表演性工作**（对比 [[02-主题/工作方法/表演型工作（Fake Work）：结构成因、AI 的两面与求真的落点|表演型工作]] 的"交接点即责任清零点"——邮件恰好是最典型的交接点）。
3. **"给 agent 看的版本"有一个隐藏成本：它会漂移。** 人看的版本会随判断更新，机器看的版本如果不同步更新，agent 就会按过期规则执行，而且执行得很自信。
4. **凭证交给 agent 读取，等于把安全边界下移到 agent 的日志与上下文。** 视频没讨论"agent 读了 1Password 之后，密码会不会出现在某个 markdown、某次对话、某个备份里"这个问题。我认为这是这套流程里风险最高的一环。
5. **"提高带宽"是有代价的。** AI 加工让输出量上一个数量级，同时也让**错误的观点被规模化传播**。他在乎"思想是我的"，但思想的质量控制并没有随产量同比提升。

## 十、可执行的动作（助手提炼，非讲者原话）

- **把 `AGENTS.md` 当路由表写，不当介绍文档写**：只留"资料在哪 / 约束是什么 / 改哪里"，删掉一切叙述性文字。
- **给每个活跃目录补一个 `index.md`**，由 agent 生成、人工只审"有没有漏"。
- **设一个"索引校验"动作**：新增笔记后要求同时更新对应索引页，定期让 agent 扫描"未被任何索引引用的文件"。
- **每次任务收尾固定说一句**："把该存的文件存一存，该更新的索引更新一下。"——把它变成肌肉记忆，而不是每次重新想。
- **想试邮件交接，先拿一件低风险事务跑通**（比如"把某份材料整理成对方要的格式并回信"），不要一上来接后台权限类工作。
