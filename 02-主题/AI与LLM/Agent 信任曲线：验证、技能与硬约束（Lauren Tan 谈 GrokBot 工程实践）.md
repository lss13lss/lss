# Agent 信任曲线：验证、技能与硬约束（Lauren Tan 谈 GrokBot 工程实践）

> [!abstract] 瓶颈不是生成代码，而是你信不信它产的；信任由「验证能力 + 技能 + 架构硬约束」三者堆出来
> Lauren Tan（X 上叫 Potato，拼写带个 e，即 @poteto；Netflix → Meta React Compiler → Cursor → GrokBot）一小时分享的核心：**如果你连一个 agent 的输出都不信任，就不可能开出一百个**。她用五个月把信任曲线推到「今天醒来，agent 已自动合并约 20 个 PR，我在 main 上事后 review」的地步，前置代价是把 GrokBot 重构到 Dune 架构的 **600 多个 PR**。方法可拆成三件事：**让 agent 自己验证**（真跑应用、抓 trace 与堆快照、开模拟器）、**把经验编码成技能**（本质就是 markdown，效果等价于「把 agent 拉进另一个潜空间」）、**把约束写进架构与 CI 而非规范**（"最短的路径就是最好的路径"，因为 agent 天生爱抄近路）。

## 一、信任曲线：并行度是信任的函数，不是意志的函数

- 信任是怎么没的：有经验的老工程师有自己的标准，而 agent 会猜、会幻觉、**「第一百次自信满满地宣称找到了确凿证据（smoking gun）」却根本不是真正的问题**——几次下来信任崩塌，然后就只能微观管理。
- 管理类比贯穿全篇（她先在 Netflix 从 tech lead 转到 EM 做了约两年）：不信任 → 微观管理 → 你也变不成事。「**如果你连一个 agent 的输出都不信任，就不可能一下开出一百个。**」
- 曲线现状：起初是和一两个 agent 贴身合作、每条输出与 tool call 都看，**无法并行**；现在则能自动合并。**上个月 1000 个 PR，这个月到 12 号已近 800 个**；第一个月效率很低，因为在认代码库。
- 她自己先承认质疑的合理性：「我相信你们很多人会问——**这些代码到底有多好**？我觉得这样质疑确实很合理。」

## 二、第一层：让 agent 会验证（不然你就是验证者）

- **验证 ≠ 跑测试**，而是 agent 能**真的把应用跑起来、像用户那样去用**：抓 CPU trace、堆快照、开 iOS 模拟器，验证用户实际看到的行为。
- 判断标准说得很实在：**「不保证它能写出好代码，但至少能让它写出正确的代码。」**
- 反面情形她入职第一周就撞上了：自己一个人用 Chrome DevTools 做性能追踪、截图、把 trace 丢给 agent，agent 自信地指认某个组件，结果不是。**「没有验证（技能），你就是验证者——也就是说你是瓶颈。」**
- 于是有了 **Control Glass 技能**（Glass 是 agent window 的内部代号）：教 agent 用 **Chrome DevTools Protocol** / Apple 模拟器工具去驱动应用。这类技能本身不难，agent 就能写。
- **真正的增量是 Feature Map**：agent 会操作但不知道「这应用有什么功能、怎么走到那儿」。Feature Map 写清楚侧边栏是什么、有哪些子功能、用户视角怎么走过去、快捷键、乃至用于 CDP 选择元素的 DOM 属性。**有了它，一句模糊反馈甚至一张截图就能映射到代码库。** `pstack` 提供了 create / maintain verification skill 来生成与维护它。

## 三、第二层：技能（把工程师的判断力编码成 markdown）

- 触发点：agent 坚称「一定是这个」，**但看 tool call 发现它根本没读应该受影响的代码**——「那一刻我就觉得再也信不了它了」，然后很容易积累成无力感。
- 管理类比的解法：团队里来了个很会写代码但**毫无业务背景、五秒前才入职**的工程师，你怎么让他有效？靠**教**，载体就是技能。
- **为什么有效（这段最值得记住）**：技能本质就是 markdown，但它编码了大量信息与指令；LLM 本质在预测下一个 token，**「当你一开始给它一些高质量的 token，它就能在更高位的空间里做模式匹配」**——推特上把这叫「把 agent 拉到另一个潜空间（latent space）」。
- `pstack` 的来历是开 Garry Tan（YC CEO，做了 `gstack`）的同姓玩笑，叫 **P-Stack（土豆堆栈）**；**不是规划出来的**，是一次次「观察到一种失败模式就固化成一个技能」长出来的。
- **Eval = 技能的单元测试**（`pstack` 里叫 Eval Playbook）：协调器写 rubric → 生成大量子 agent 到**各自独立且「巧妙命名」的目录**里，**让子 agent 不知道自己正在被评估**（「因为 agent 真的能看出来，一旦看出来它们会改变行为」）→ 打分 → **用不同模型的评判 agent 交叉验证** → 爬山式循环到满分。
- **维护技能很难，需要品位和观察**：当好一个「后座司机」，像结对编程那样盯着看；实操是**打开所有 tool call、读代码读取与 thinking blocks**，从失败点里提炼技能。

## 四、第三层：把约束写进架构与 CI（最硬也最容易被忽略的一层）

- **Dune** 是给 GrokBot 做的架构代号，心智模型是「**Electron 应用的 Next.js**」，专为 agent 写代码设计。CI「很烦人」，因为什么都查：
  - **禁用 useEffect**（React 最大的 footgun）；**禁用代码注释**——理由是 99% 的 agent 注释只是在描述历史过程、与代码无关（她举的例子：随口一句「这个 PR 很烂」最后被 agent 写成代码注释）。
  - **进程边界硬隔离**：Electron 渲染要保持 60fps，每帧须在 **16 ms** 内完成；隔离没做好就会把重计算/重 IO 拉进渲染线程导致掉帧。所以直接分 `ElectronMain` / `ElectronRenderer` 目录，并用 **import CI 检查依赖图**禁止跨进程 import。
  - **Feature 共置**：feature / entry points / transcript cards 是框架里的「名词」，创建方式固定、一个功能的全部代码都在同一目录——**「为最笨的 agent 设计的，你根本不用思考」**。
- **一句话原则：「最短的路径就是最好的路径。」** agent 天生爱抄近路，那就让近路恰好是正确解法。
- **五层执行强度（强 → 弱）**：① 代码库本身（架构/目录/禁止依赖，最强，因为 agent 最爱复制现有模式）→ ② 静态分析：CI / lint（针对观察过的糟糕模式）/ 编译期诊断 → ③ Rules 与 BugBot（AI review，软，可能忘）→ ④ 技能 → ⑤ 风格指南/代码分割指南（最软）。
  - 「**如果你只有 rules、BugBot、技能和代码分割指南，代码库变得一团糟只是时间问题。**」要投资那些**难但强制**的东西。
  - Rust 的类比：严格编译器 + borrow checker，「**代码能编译，它大概率就能跑、质量也不错**」——编译器给了你不亲自 review 的信心。
  - **最糟的是靠人 enforce**：每当你在 PR 上写下「你不应该这样做」，都应视作**代码异味**→ 改成 lint 规则、改成 CI 失败、或者把这个可能性彻底消掉。
- 顺序建议：**先本地（你看得见交互）再云**；她的 **Benny** 例子是接到 bug 报告后在云端自己的电脑上跑 Cursor、用同一套 Control Glass 技能复现，有时发现 bug 在 main 上已修复——一条信息省掉一小时。**别在信任不足时直接开一百个云代理**，那只是烧 token。

## 五、代价与收益：一道 ROI 题

- 「我在一个 AI 实验室工作，**那里有无限的 token**」——她明确说不必照抄。对工程负责人/初创公司这是 ROI：**前期烧 token（尤其重构），换来的是保持精简、不变成 Meta 那样一万人的工程组织**。
- 关键是这笔钱买的是**以前做不到的事**：一个人想在代码库里落地这种级别的约束，以前要花好几年。回报也不止她自己——PM、设计师、GTM 也能安全贡献。
- 一条产品侧信息：**Grok 4.6 发布，每 token 成本与 4.5 相同**——「这是 Cursor 和 SpaceXAI 真正想优化的地方：**成本与智能之间的帕累托前沿**」，不是造最大的模型，而是「够聪明、推理不贵」的甜点。
- 顺带一个角度看 GrokBot：**「GrokBot 基本上就是非技术人员的 Cursor 时刻」**（界面像 iMessage、每个 agent 有自己的身份和名字、可编排）。PM 也在提代码——「这里有个 bug，我修好了，你能看一下吗」。她的判断是：这恰好证明 Dune 那套严格约束撑得住，让非工程专业的人也能高水平贡献。

## 值得保留的两个判断

1. **"你在 PR 上留下的每一句人工评论，都是一个待修复的系统缺陷"**——把软约束升级为机械约束（lint/CI/架构），否则代码库必然退化。这条与个人能力无关，是可持续性问题。
2. **"对你就是这样"的逆向用法**：不要把"agent 不行"归结为模型不够强；先问它在哪个层上失手。99% 情况下可以从架构和静态分析层直接消掉。
