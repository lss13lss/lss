# Agent 信任曲线：验证、技能与硬约束（Lauren Tan 谈 GrokBot 工程实践）

> [!abstract] 把信任建在可验证的行为与可执行的约束上
> Lauren Tan 的经验是：先让 Agent 能运行真实产品、验证改动；再把业务背景和工程判断写成可评测的技能；把反复违反的约束进一步固化为架构与 CI。并行与自动合并是她积累信任后的结果，不能只复制结果而省掉前面的投入。

## 一、信任不足为什么限制并行

她将 Agent 管理类比为带新人：会写代码却缺业务背景，还可能在没读相关代码时自信地声称找到根因。工程师随后不断检查、传截图、补控制台错误，自己成了验证瓶颈。

她自述一个月合入约 1000 个 PR，并曾醒来发现约 20 个 PR 已自动合并。但她也说，重构到新架构投入了 600 多个 PR 和大量 Token。PR 数是个人自述的活动指标，不能直接等于相同数量的独立功能、生产率倍数或质量证明。

更值得关注的因果顺序是：**补齐验证和约束 → 输出更可信 → 人减少逐步盯守 → 才能承担更多并行。** “信任曲线”是她对自身经历的非科学示意，不是各团队都服从的增长规律。

## 二、验证技能要把反馈闭环交给 Agent

她的 verification 包括启动产品、复现操作、采集 CPU trace 和 heap snapshot、使用模拟器，依据真实结果再修改。测试并不保证设计优雅，却能减少没有运行依据的猜测。

Control Glass 用于操作 Cursor 内部代号为 Glass 的 Agent 窗口。只具备点击能力仍不够：Agent 不知道产品有哪些功能，也不知道“侧边栏很卡”应该怎样复现。

**Feature Map 是连接用户语言与可执行操作的上下文。** 它包括功能和子功能、导航路径、快捷键、选择元素需要的属性等。用户模糊报告或截图由此能对应到可复现步骤。PStack 中还有创建与维护验证技能的机制；产品变更后，地图也要更新。

她举的云端 Benny 例子很具体：自动复现 bug，发现 main 上已修复，团队只需发布新构建。价值是获得可行动的证据，而不是生成一段很肯定的诊断。

## 三、技能从真实失败长出来，并要经过评测

PStack 最初不是预先规划的一整套体系。她观察 Agent 没读相关代码、反复猜测等失败后，将所需行为与背景逐渐写成技能。她用“把 Agent 拉到另一个潜空间”解释高质量上下文的作用，这是直觉类比，不是本期验证过的模型内部机制。

她将 eval 类比为技能的单元测试，流程包括：定义 rubric → 在隔离目录运行任务 → 检查行为是否符合要求 → 跨模型比较 → 迭代修改。材料还提到避免让被测 Agent 从目录名称识别自己在被测，减少测试提示对行为的干扰。

要区分两个问题：**任务这次做对了吗？技能在多种任务中稳定有效吗？** 一次自测通过只回答前者。旧稿把反复修改到“满分”写得像充分保证，本次改为看评测覆盖与实际结果；Agent 评判也应被检查，不能自评满分就推出可安全上线。

维护需要观察真实工具调用、代码阅读过程与输出。她的管理类比是主厨设计厨房、分派任务，而不是亲自完成每道菜。

## 四、把反复犯的错升级为硬约束

她认为 Agent 很爱复制现有模式、选择最短路径，所以最好让最容易走的路径同时符合工程要求。

| 层次 | 视频中的做法 | 为什么比反复提醒更可靠 |
|---|---|---|
| 代码结构 | Feature 代码共置，固定入口与功能组织方式 | 直接降低找错位置、拼错模式的机会 |
| 架构边界 | 分开 Electron 主进程与渲染进程目录 | 让执行位置与依赖关系更清楚 |
| 静态约束 | 检查依赖图，禁止不合法跨边界 import | 不符合就使 CI 失败 |
| 规则、技能与 AI review | 补背景、指导步骤、检查问题 | 可帮助推理，但可能遗忘或漏判 |
| 风格文档 | 描述约定 | 若缺执行机制，长期容易偏离 |

她用 Electron 性能举例：60 fps 的单帧预算约 16.7 ms，重计算或 IO 进入渲染路径会破坏体验。Dune 将边界固化为目录和依赖检查。她同时承认 Agent 窗口尚未采用同样架构，性能会频繁回退，计划把经验迁回去；不能写成整个产品已经解决这类问题。

她还举禁止 useEffect、禁止代码注释等规则，目的是压制她观察到的特定失败模式。这些属于该代码库的取舍，不是所有 React 项目或所有注释都应禁止。

可复用原则：**对能机械判定、反复发生的错误，把人工提醒转成 lint、CI 或结构限制。** 旧稿“每一句人工评论都是系统缺陷”“99% 情况可消掉”过度外推；需求澄清、设计权衡、产品判断仍可能需要人。

## 五、自动化有前提，也有成本

她建议先本地验证，因为人能看到 Agent 实际怎样操作；建立信任后再迁到云端，提高团队共享和并行能力。她明确不建议从不信任单个 Agent 直接跳到数百云 Agent。

她也承认自己在 AI 实验室有充足 Token，别人不必照抄。投入回报要算前期重构、验证基础设施、后续维护，以及省下的人力和减少的故障。自动合并是她的个人工作实践，不是本页授予其他项目的默认权限。

原稿关于模型型号、成本相同和公司关系的段落，与工程主线无关，且双轨自动转写不足以核实，本次不保留为产品事实。Rust 类比也只能说明编译约束有价值，不能写成编译通过就证明业务行为正确。
