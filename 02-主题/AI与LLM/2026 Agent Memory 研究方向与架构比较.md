# 2026 Agent Memory 研究方向与架构比较

## 核心结论

2026 年 Agent Memory 的研究重心，已经从“存进去、搜出来”转向“怎样把记忆作为一个持续运行、可更新、可审计的系统”。但这不意味着 RAG 被淘汰，而是 RAG 被降级成整个记忆生命周期中的一个部件。

Claude 式纯文本记忆和 Mem0 并不是同一层面的互斥方案：

- 纯文本解决：真实状态放在哪里，怎样被人审计和修改。
- Mem0 解决：怎样自动抽取、建立索引和找到候选记忆。
- MRAgent 解决：复杂问题下，怎样沿着中间证据继续搜索。
- MSCE 解决：怎样把反复成功的经验转变成可执行流程。
- 共享记忆研究解决：谁能读写、旧事实怎样失效、不同 Agent 怎样避免互相污染。

对当前 [[05-成长/对话成长/上下文系统/CURRENT|个人上下文系统]]，最合适的路线不是在“纯文本”和“RAG”之间二选一，而是保留 Markdown/Git 作为真实来源，在出现明确召回瓶颈后，再逐层增加关键词、BM25、向量或图索引。

## 2026 年研究主要集中在五个方向

### 1. 从“记忆库”转向完整生命周期

[Agentic Context Management](https://arxiv.org/abs/2607.21503) 把系统分成 architecting、ingesting、scoping、anticipating、compacting/consolidation 五类动作；[Mi-Memory](https://arxiv.org/abs/2607.18975) 又把重点扩展到多模态证据、策略演化、部署和审计。

这一方向的关键认识是：很多记忆失败并不发生在检索阶段。

- 重要信息在写入时已被摘要丢失。
- 新事实进入后，旧事实没有失效。
- 检索到了证据，但在上下文组装时被过滤。
- 一个用户或项目的记忆泄漏到另一个范围。
- 摘要看似正确，却没有来源，无法判断可信度。
- 删除了原始事实，却没有删除派生摘要、画像和缓存。

这类研究适合提供架构框架，但证据等级需要区分：Maximem 是厂商作者的预印本，Mi-Memory 是小米团队的技术报告，二者的自报 benchmark 不能直接作为产品优劣证明。

### 2. 从一次性检索转向主动重构

[MRAgent](https://arxiv.org/abs/2606.06036) 的重点不是单纯“使用图”，而是把检索变成循环：

> 当前问题 → 找第一批线索 → 根据线索形成新查询 → 继续扩展或剪枝 → 判断证据是否充分

论文在 LoCoMo 上报告了最高约 23.3% 的相对提升；在 LongMemEval 的特定配置下，每样本 token 从 A-Mem 的 632k 降到 118k，但运行时间仍为 586 秒，并不比 Mem0 的 533 秒更快。

优点：

- 适合多跳、时间关系和模糊线索。
- 不要求第一次检索就命中全部证据。
- 能根据中间发现改变检索方向。

缺点：

- 延迟会随搜索深度增加。
- 依赖较强模型进行路由和停止判断。
- 当前版本缺少完善的更新和遗忘机制，图会持续增长。
- 对简单偏好或单一事实查询明显过重。

[AMA-Bench](https://arxiv.org/abs/2602.22769) 从另一面支持了这个方向：真实 Agent 轨迹包含行动、工具结果、状态变化和因果关系，不只是自然语言对话；纯相似度检索容易丢失“为什么发生”和“哪个操作导致哪个状态”。

### 3. 从“回忆经验”转向“形成技能”

[MSCE](https://arxiv.org/abs/2607.16621) 把经验分为三个层次：

- L1：可追溯的执行轨迹。
- L2：从多次轨迹归纳出的程序策略。
- L3：关于环境结构和约束的稳定认识。
- Skill：经过证据、收益和适用范围验证后，才晋升的可执行能力。

如果 Agent 每次都检索过去经历，再重新推理一遍“怎么做”，记忆只是减少遗忘，没有形成复利。把稳定经验转成 Skill，才可能真正减少重复推理。

主要风险：

- 错误经验可能被固化为程序。
- 适用边界判断错误时，技能会在错误场景被调用。
- 论文中的收益评估仍是启发式信号，不是因果证明。
- 反思、策略抽取和技能生成依赖 LLM，会增加成本与不确定性。

因此，这条路线适合“反复执行且可验收的工作流”，不适合把偶然偏好或一次成功直接升级成技能。

### 4. 从单 Agent 记忆转向共享但受治理的记忆

共享记忆的核心已经不再是“所有 Agent 共用一个向量库”，而是：

- 哪些记忆私有，哪些可以晋升成团队知识。
- 谁拥有写权限。
- 新事实如何取代旧事实。
- 每条结论能否追溯到原始来源。
- 如何阻止跨用户、跨项目和跨 Agent 泄漏。

[Governed Shared Memory](https://arxiv.org/abs/2606.24535) 总结了四种典型故障：越权泄漏、过期传播、矛盾持续存在、来源链坍塌。论文还披露了其系统曾出现“按 ID 读取时绕过子租户范围检查”的真实缺陷，这类生产失败证据比单一准确率更有工程价值。

[Meko](https://www.yugabyte.com/blog/meko-data-infrastructure-for-agents-that-work-and-learn-together/) 更适合被理解成企业共享数据基础设施，而不是新的记忆算法。其底层默认使用 Mem0，并在上层增加 per-agent scope、共享知识、conversation 和 trace。

### 5. 从只看准确率转向系统成本与可验证性

[Are We Ready For An Agent-Native Memory System?](https://arxiv.org/abs/2606.24775) 统一评测了 12 个系统，并把记忆系统拆成四个模块：

| 模块 | 真正需要回答的问题 |
|---|---|
| 表示与存储 | 保存原文、摘要、事实、树还是图 |
| 抽取 | 哪些内容值得留下，抽取过程损失了什么 |
| 检索与路由 | 关键词、向量、图、混合还是 Agent 搜索 |
| 维护 | 怎样更新、合并、失效、遗忘和版本管理 |

这项研究更重要的结果不是哪个系统排名第一，而是：

- 没有一种架构在所有负载上占优。
- 原始证据保留通常比更深的抽象更重要。
- 图结构擅长事实更新和实体关系，但不天然擅长时间推理。
- 强摘要会损坏精确日期、名称和跨会话证据。
- 局部更新比全局重建更有成本优势。
- 长上下文在部分需要精确时间线的任务上仍优于记忆系统。

## Claude 式纯文本与 Mem0 的理性比较

| 维度 | Claude 式文本＋渐进加载 | Mem0 式混合检索 |
|---|---|---|
| 可审计性 | 很强，文件可读、可 diff、可回滚 | 取决于平台和元数据设计 |
| 精确更新 | 人工维护时很强 | 自动化强，但可能产生冲突或重复事实 |
| 语义召回 | 依赖目录、摘要、关键词和模型判断 | 向量＋BM25＋实体匹配更强 |
| 多跳关系 | 弱，除非模型主动连续读文件 | 图增强后更强 |
| 写入成本 | 低，但需要组织和整理 | 抽取、嵌入、去重有额外成本 |
| 解释失败 | 容易看出读取了什么文件 | 需要检查抽取、索引、召回等多个阶段 |
| 规模扩张 | 文件多后路由效果会下降 | 更适合大规模候选集合 |
| 典型错误 | 没读到、摘要没提示、文件过时 | 错抽取、错召回、旧事实共存、黑盒排序 |

Claude Code 的正式机制与“摘要索引＋按需加载详情”基本一致：`MEMORY.md` 只加载前 200 行或 25KB，详细主题文件启动时不加载，由模型按需读取；文件都是可编辑 Markdown。参见 [Claude Code 记忆文档](https://code.claude.com/docs/zh-CN/memory) 和 [Anthropic 的上下文工程文章](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)。

Mem0 到 2026 年已经不能准确概括为简单的向量 RAG。新版采用单次 ADD-only 抽取，并行融合语义、BM25 和实体匹配；图用于给相关实体的记忆加权。参见 [Mem0 新版算法说明](https://mem0.ai/blog/mem0-the-token-efficient-memory-algorithm)。

## 对当前个人上下文系统的建议

### 现在保留

1. Markdown/Git 继续作为唯一真实来源，原始会话保持不可变。
2. `BOOTSTRAP.md` 只保留范围、当前状态和详情入口。
3. Observer 只生成候选观察，不直接覆盖已确认事实。
4. 画像、当前状态、观察记录和原始会话保持不同的可信度层级。

### 下一步按真实失败增加能力

1. 先增加关键词、BM25 或 SQLite FTS 这类可解释索引。
2. 当实际日志证明“同义表达找不到”成为主要失败原因时，再增加向量索引。
3. 当多跳实体关系成为主要瓶颈时，再考虑轻量图或主动重构。
4. 向量库和图都只作为派生索引，每个节点必须指回原始对话、日期和对应 Markdown。
5. 只有重复成功、适用边界明确且可以自动验收的经验，才晋升为 Skill。

这个策略的核心是：先建立可靠的真实来源和更新机制，再根据召回失败补索引；不要先部署复杂记忆框架，再反过来迁就它的世界观。

## Benchmark 与证据边界

LoCoMo、LongMemEval 的分数会被回答模型、judge、top-k、是否包含拒答题和提示词显著影响。

例如，Mem0 当前公开评测提示中包含 “chandelier counts as jewelry”等 benchmark 特定规则。因此这类分数代表“检索＋提示＋回答模型＋判分器”整套配置的表现，不能直接视为纯记忆架构性能。参见 [公开评测提示](https://github.com/mem0ai/memory-benchmarks/blob/4b61c5d31b9c668a12b4f5e78064248a02c82d2b/benchmarks/longmemeval/prompts.py#L138-L147)。

本报告的置信度：

- 对“研究正在转向生命周期、主动检索、技能化和治理”的判断：较高。
- 对“某个系统在特定 benchmark 的绝对分数”的判断：中等。
- 对“各家系统的统一性能排名”的判断：低。

真正值得持续观察的不是谁宣称 SOTA，而是三件事：

1. 写入时是否保留足够的原始证据。
2. 更新时是否可以纠错、失效和回滚。
3. 调用时是否能解释为什么加载了这条记忆。
