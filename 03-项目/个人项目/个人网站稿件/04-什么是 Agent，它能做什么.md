# 什么是 Agent，它能做什么

从“帮我安排一次出差”这样的普通请求出发，看 Agent 和聊天窗口差在哪：它会拆步骤、用工具、核对结果，也需要你先给够背景。

很多人第一次听到 Agent，会以为它是更会聊天的 AI。更贴近的说法是：它拿到的不再是一个问题，而是一件要完成的事。

## 从 AI 到 Agent

AI（人工智能）指让机器做原本需要人来判断的事：看懂文字、认出图片、从数据里找规律。这几年常被提起的，是其中处理语言的一支。

这一支的底层叫 LLM（Large Language Model，大语言模型），是读过海量文字、学会「顺着前文接着往下写」的程序：给一段话，还一段话。概括、改写、起草、按条理分析都擅长，但它自己不会去查网页、翻你的文件，也不会替你下单。

平时打开的豆包、元宝、DeepSeek、Kimi，以及常在网上看到的 ChatGPT、Claude，大多是把这类模型包成的对话产品：一个输入框，一问一答，主要交付一段文字。

> [!note] 表 1 · 几个常听到的名字，大致各指什么

| 常看到的名字 | 大致指什么 | 一个直观的理解 |
| --- | --- | --- |
| AI | 一个很大的领域 | 让机器做原本要人来判断的事；聊天只是其中一小块 |
| LLM / 大语言模型 | 处理文字的底层模型 | 读过大量文本，擅长接着写、概括、改写、分析 |
| 豆包 / 元宝 / DeepSeek / Kimi | 常见的对话助手 | 打开就是一个输入框，主要交付一段文字 |
| Codex / Claude Code | 更偏编程的 Agent | 会读代码、改文件、运行后看结果，把活往前推 |

同一个名字有时既指模型，也指用模型做成的产品；Claude、ChatGPT 这类还可能被接进 Agent 的工作流。产品在变，功能互相重叠，边界并不固定。

AI 是领域，LLM 是处理文字的模型，对话产品把模型包成一个输入框。Agent 是在模型之外，再加上目标、工具和一个能反复检查的循环。

## 先从一个普通请求说起

假设你对 AI 说：“帮我安排下周去上海出差。”在常见的聊天窗口里，你会得到一段建议：航班怎么选、住哪个区域方便、两天的会怎么排才合理。写得清楚，但到这里就结束了——查时刻表、比价、看日历冲突、下单，还是你自己做。

如果换成 Agent，你期待的不是一段更漂亮的建议，而是这件事被往前推：它去查可用的班次、对照你日历里已有的安排、把几个方案整理成一张待你确认的清单，确认之后才去执行。

差别不在措辞，而在它能不能围绕同一个目标多做几步。这个例子只是用来讲清区别，不是对某个产品的效果测试。

## Agent 到底是什么

一句话：Agent 是拿到一个目标之后，能自己决定下一步、调用工具、再根据结果调整做法的程序。它通常不是一种更聪明的模型，而是把模型放进了一个「可以行动、可以回头检查」的流程里。

- 有目标：要完成的是一件事，而不是回答一个问题。「帮我写篇文章」和「把这份记录整理成三条能用的判断」，是不同的起点。
- 能决定下一步：先查资料还是先动笔，由当前进展决定，不是一开始就写死。
- 能用工具并检查结果：搜索、读文件、调接口、跑一段代码都算；结果不对就换一种做法，或者停下来问人。

> 模型负责给出判断，Agent 负责把判断拿去试，再看看行不行。
>
> — 本文的讲法

所以同一个模型，接在聊天框里是聊天助手，接上工具和一个循环，就成了 Agent。能力边界常常不在模型本身，而在它被允许做什么、这一次能拿到什么信息。

## 一轮工作是怎样发生的

把一轮拆开看，通常是四步，而且会重复好几轮，直到目标完成，或者该由人来决定。

关键在「核对结果」：工具返回的内容未必对，网页可能过期，文件也可能不是你要的那份。Agent 要判断这一步是否让自己更接近目标，然后决定继续、换方法，还是把问题交回给你。

也因为这个循环，Agent 往往比一次性回答更慢、更费算力，还会留下中间过程。它适合「值得多走几步」的任务；随口问一句的事，用它反而绕远。

## 它能做什么：三类常见任务

不必记产品名单，看任务形状更容易判断什么时候值得用。

> [!note] 表 2 · 三类适合交给 Agent 的任务

| 任务形状 | 一个具体例子 | 为什么适合 Agent |
| --- | --- | --- |
| 信息要现查、还要互相核对 | 「找出近三个月关于 X 的公开资料，整理成一张对照表」 | 要多轮检索、去重、看来源，结果之间还会互相影响 |
| 步骤多，后一步依赖前一步 | 「把这份会议记录拆成待办，按负责人分好，写进文档」 | 上一步的产出决定下一步做什么，一次性回答很难接住 |
| 要说动外部工具真的执行 | 「把表格里的数据画成图，存到指定目录」 | 重点不是描述怎么做，而是把文件真的生成出来 |

反过来，也有它做不好的：目标本身模糊、需要你替它拍板、或者结果好不好根本无法验证的事，多走几步只会偏得更远。这类任务更适合先由人把问题说清楚。

## 怎么用好它：把背景和边界先给足

同一个 Agent，给的信息不同，表现差别很大。下面几条不是技巧清单，而是让它的判断有依据。

- 说清目的和读者，而不只是「帮我写」。
- 把已有材料、已经试过的方法、不想要的结果一起给它，减少它猜的部分。
- 说明哪些动作必须先问过你：花钱、发邮件、删改文件。
- 要求它标出来源和仍不确定的地方，方便你回头核对。

这些其实都是「上下文」：不是什么玄学，就是这一次判断时它手里有哪些信息。你给得越具体，它越不用猜；但信息给得足，也不保证结论一定对，仍需你自己看一遍。

> 先让它说清打算分几步、需要什么，再决定要不要让它继续。
>
> — 本文的讲法

## 一个可以马上试的小任务

不必先搭系统，也不用懂实现。挑一件你最近反复解释过的小事，比如「把上周的读书笔记整理成三条能用得上的判断」，把背景、已有笔记和你不想要的样子一起给它，先请它说出打算分几步、需要哪些信息。

看清它「打算怎么做」，比直接看最终答案更容易判断值不值得继续用。如果它第一步就理解偏了，趁早纠正，比等一长串结果出来再返工省事。

这也是我自己在做的事：把已经想清楚、反复用到的背景留下来，让下一次协作不必从头讲起。
