# 什么是 Agent，它能做什么

刷短视频、看文章，或者听同事讨论时，我们会遇到 AI、大模型、Agent 这些词，也会听到豆包、DeepSeek、Kimi 等名字。它们经常一起出现，却不都在说同一件事。

要理解 Agent，可以先分清：我们说的是什么技术，平时打开的是什么产品，以及这个产品怎样帮我们完成一件事。

## 一、AI 和大模型，分别在说什么

AI 是人工智能的简称，是一个很大的技术领域。识别图片里的物体、把语音转成文字、根据数据作出预测，都属于这个领域的应用。我们现在熟悉的 AI 对话，只是其中一种。[关于 AI 的基本范围，可参见 IBM 的说明。](https://www.ibm.com/think/topics/artificial-intelligence)

大模型是 AI 领域中的一类模型。这里的“模型”，可以先理解为：一个经过数据训练，能够根据输入生成输出的计算系统。大模型也有不同类型，语言模型是其中一类，并不涵盖所有处理图片、声音等信息的模型。

大语言模型的英文缩写是 LLM。它从大量数据中学习语言的规律与关联，根据当前输入生成后续内容。我们让它概括文章、翻译句子、起草邮件，就是在使用这类能力。它能生成通顺的解释，但通顺不等于事实正确。[Google 的语言模型入门说明介绍了这一基本机制。](https://developers.google.com/machine-learning/crash-course/llm)

理解到这里，可以先记住这个关系：AI 是更大的领域，大语言模型是其中的一类技术。日常所说的“大模型”，有时指语言模型，有时也包括其他类型，要结合语境看。

## 二、平时打开的产品，和模型是什么关系

当我们说“打开豆包问一下”“在 Kimi 里上传一份文件”时，说的是自己正在使用的应用或网站，也就是产品。

产品会把模型能力、操作界面以及其他功能组织起来。输入框负责接收你的问题，文件功能负责接收材料，背后的模型参与处理信息、生成回答。要查询网页或修改文件，还需要相应的工具支持。

可以用一件小事来区分：**写出“建议把会议改到周三”的句子，与真的修改日历，是两个不同的动作。**前者可以是模型生成的回答，后者还需要产品连接日历，并获得相应权限。[Google Cloud 对 Agent 组成的介绍，也区分了模型与工具的作用。](https://cloud.google.com/discover/what-are-ai-agents)

因此，评价一个产品能做什么，不能只看它用了哪个模型。还要看它接入了哪些工具，能拿到哪些材料，以及允许执行哪些动作。

模型名和产品名有时会共用一个品牌名称。遇到不熟悉的名字时，可以先看对方是在谈“背后的模型”，还是“我打开来使用的软件”，不必急着记下一张产品名单。

## 三、Agent 增加了怎样的工作方式

Agent 常被译为“智能体”。这个词在不同场合的用法不完全一致。本文主要讨论基于大语言模型的 Agent：它接到目标后，能在允许的范围内决定下一步，使用工具，并根据得到的结果继续推进任务。

这里重要的是，下一步不一定完全由人预先写死。例如，资料不够时继续查找，发现冲突时回头核对，需要你作决定时停下来询问。这样的过程，和每一步都按固定规则执行的自动化流程有所区别。[Anthropic 对工作流与 Agent 的区分采用了这一思路。](https://www.anthropic.com/research/building-effective-agents)

所以，Agent 不必对应一个全新的模型，也不一定有一个与聊天软件完全不同的界面。一个聊天窗口背后，也可以运行这样的任务过程。判断时要看它怎样工作，不能只看有没有输入框。

把几个概念放在一起，可以这样理解：

| 概念 | 在描述什么 |
| --- | --- |
| AI | 包含多种技术与应用的领域 |
| 大语言模型 | 处理语言、生成内容等能力所依赖的一类模型 |
| 产品 | 用户实际打开和操作的软件，将模型与其他功能组织起来 |
| Agent | 围绕目标，判断下一步并根据执行结果推进任务的系统 |

它们之间存在组合关系：一个产品可以使用大语言模型，也可以提供 Agent 功能。它们不是四个互相替代的名字。

## 四、用安排出差来理解它的过程

假设你提出：“帮我安排下周去上海出差，周二上午十点有一场会议。”

如果这次交互只生成一份建议，它可能告诉你提前一天到、住在会场附近，以及需要考虑哪些因素。你可以参考这些建议，再自己查班次、比较价格、检查日程。

如果系统具备查询交通、读取已授权日历等工具，并以 Agent 的方式推进任务，过程可能是这样的：

1. **补齐条件。**确认出发城市、会场地址和预算；信息不够时先问你。
2. **查询可选方案。**查找班次，对照你已有的日程。
3. **根据结果调整。**发现某个方案与日程冲突，就换一个；预算内没有合适选择，就把限制告诉你。
4. **整理待确认结果。**把可选方案、时间和费用列出来，交给你决定。

这是一段用于理解的假设情景，不代表某个产品已经能完成其中所有动作。如果还要订票，则需要相应的预订能力，并明确由你确认购买。

这个过程可以概括为：**看已有信息 → 判断下一步 → 使用工具 → 根据返回结果继续判断。**结果仍可能有误，检查环节也不保证一定发现错误。Agent 可以在中途需要你补充信息，也可以停在一份待确认方案上；并不是必须全程无人参与才算 Agent。[关于工具调用、计划调整和人的参与，可参见 IBM 的 Agent 说明。](https://www.ibm.com/think/topics/ai-agents)

## 五、它能做什么，又有哪些限制

沿着上面的过程，可以理解一些可能的用途。以下都是示意，能做到哪一步取决于具体产品和权限。

- **整理资料。**围绕一个问题查找材料，发现说法不一致时继续核对，最后整理出带来源的说明。
- **处理工作文件。**读取指定目录中的会议记录，找出尚未明确负责人的事项，请你补充后再生成任务清单。
- **处理表格或代码。**检查数据后选择合适的处理方法，生成文件，再根据检查结果修改。

这些任务往往需要几步配合，也可能在进行中遇到原先不知道的情况。Agent 的用途之一，就是帮助处理这样的过程。

但“步骤多”不代表必须用 Agent。如果只是改写一句话，一次回答可能就够了；如果每次都按完全相同的规则处理，固定流程也可能更合适。多轮执行通常还会增加等待时间和使用成本。[Anthropic 建议根据任务需要选择复杂度，而非默认采用 Agent。](https://www.anthropic.com/research/building-effective-agents)

它也不会因为能够行动，就自动理解你的所有意图。它可能读错材料、采用过期信息，或对模糊目标作出不合适的判断。涉及付款、发出消息或修改重要资料时，需要事先明确权限和确认方式。

## 六、为什么理解 Agent 之后，还要理解上下文

还是安排出差这件事。即使它能查班次，如果不知道你的预算、不知道你不想赶早班车，也不知道这次会议的具体安排，就很难给出适合你的方案。

这些信息属于 Context，也就是上下文。放在与 AI 协作的场景里，可以先理解为：**它这一次处理任务时，实际能参考的信息。**其中可能包括你的要求、提供的材料、前面的交流，以及工具刚查到的结果。[Anthropic 的上下文工程说明讨论了这些信息如何共同影响模型的行为。](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

“材料保存在我的电脑里”和“AI 这次已经看到了材料”是两回事。同样，聊过一次，也不意味着所有工具以后都会自动记住。相关信息需要通过提供、读取或检索等方式，进入这一次的任务。

这也是我想长期做个人上下文积累的原因：把自己读过的、想过的、做过的，以及已经确认的偏好和经验逐渐留下来。在后来的问题里，再找到合适的部分，用来帮助自己判断，也帮助 AI 理解我的实际情况。

这里有两个相连的过程：平时积累和更新自己的材料，做具体事情时选择相关信息。积累不必一次完成，也不是每次都把所有笔记交给 AI。材料是否相关、是否仍然准确，比单纯堆得多更值得关注。

## 七、接下来可以了解什么

理解这些概念之后，再看到一个新的 AI 产品，可以分别去看：它使用什么能力，能接触什么信息，能执行哪些动作，以及哪些地方仍然需要自己判断。这样更容易读懂它的介绍，也更容易判断它和自己的工作、生活有没有关系。
